[3. RV-01: 저장 충돌 후 최신 체크포인트로 복구]
먼저 현재 제품 코드와 실제 UI 경로에서 다음 조건을 재현해줘.
- 동일 프로필·런을 세션 A와 B에서 연다.
- A가 sequence n일 때 B가 유효한 명령 두 개를 저장해 n+2로 진행한다.
- A에는 양수의 미저장 경과시간을 둔다.
- A의 명령 재시도, 메뉴 이동의 자동 저장, 단순 화면 새로고침으로
  최신 저장에 복귀할 수 있는지 확인한다.

충돌이 재현되면 '저장된 여정 다시 불러오기' 같은 명시적 복구 동선을 연결해줘.
문구 비교가 아니라 구분 가능한 오류 종류/결과로 stale 상태와 일시적 I/O 실패,
손상 파일·지원하지 않는 저장 형식·다른 프로필을 구별해줘.
모든 MetaCommandException을 저장 충돌로 취급하지 마.

재로드 전에 오래된 세션 저장을 강제하지 마.
현재 저장을 읽고 검증해 복구 후보를 준비한 뒤에만 Session과 화면을 교체해줘.
로드 실패 시 기존 파일·메모리 상태를 지우지 말고 재시도/복구 안내를 유지해줘.
이전 표시 토큰과 연출 콜백은 무효화하되 새 화면의 입력 잠금을 건드리지 마.
다른 런으로 교체되었거나 이미 정산된 경우에는 상태를 확인해 적절한 화면으로
안내하고, 이전 런의 명령을 새 런에 적용하지 마.

필수 검증:
충돌→안내→재로드→최신 runId/sequence로 재개하는 실제 UI 회귀,
주사위·카드·보상·정산 재실행 없음, stale 입력 거절,
일반 I/O 실패의 확정 전 무변경, 재로드 실패 시 원본 보존.

[4. RV-02: 손상 프로필의 원본 보존과 최소 복구 UI]
프로필 손상 시 자동 초기화하지 않는 현재 원칙을 유지하면서
'다시 읽기'와 '검증된 백업 복구'를 구분해줘.
아직 백업 기능이 없다면 동일 LocalDevelopment 프로필의 마지막 정상본을
최소한으로 보관하는 경로를 추가해줘. 매 프레임 백업이나 무한 파일 축적은 피하고,
보관 수·대상·실패 처리를 PLAN에 명시해줘.

정상 확인을 마친 문서만 백업 후보로 사용하고, 손상된 현재 파일 때문에
기존 정상 백업이 덮어써지지 않게 해줘. 백업 쓰기 실패로 기존 프로필이나
마지막 정상본이 지워져서는 안 돼. 보관 실패 시 성공 안내를 하지 마.

복원은 schema·체크섬·profileId·LocalDevelopment 권한·문서 전체 유효성을
검사하고, 복원 시점과 그 이후 진행이 사라질 수 있음을 안내한 뒤
플레이어가 명시적으로 확인했을 때만 수행해줘.
손상 원본을 별도로 보존하는 데 실패하면 덮어쓰기를 진행하지 마.

프로필·현재 런·시작 기록·정산/명령 receipt를 같은 시점의 문서 전체로 복원해줘.
프로필 잔액만 복원하거나 서로 다른 시점의 영수증·런을 합치지 마.
기존 쓰기 잠금과 원자 교체를 재사용하고, 복원 도중 기존 세션이나 미결 요청이
복원본을 다시 덮어쓰지 않도록 소유 세션을 정리하고 재로드해줘.
복원 전 대기 요청은 결과 확인 없이 재실행하지 마.
진행 순번이나 revision이 과거 값으로 돌아가서 오래된 토큰이 다시 유효해지는
경우도 시험해줘. 필요하면 최소한의 복구 세대/소유권 검사로 차단하되,
과거 receipt를 삭제·위조하거나 복원 전 세션을 자동 병합하지 마.

백업이 없거나 검증을 통과하지 못하면 원본 보존·안내·재시도까지 제공해줘.
임의 JSON 가져오기, 프로필 삭제/초기화, 운영 계정 복원은 구현하지 마.
이 복구 기능은 로컬 장애 대응이며 치트·백업 롤백 방지로 주장하지 마.

필수 검증:
정상/손상/백업 없음/백업 손상/다른 프로필/미지원 버전,
백업 또는 복원 쓰기 실패, 확인 전 파일 무변경,
같은 시점의 프로필·런·receipt 복원, 정산된 결과의 재지급 없음,
복원 전 세션·요청의 늦은 쓰기 방지. 실제 사용자 저장을 손상시키지 말고
격리 임시 저장과 실패 주입으로 검사해줘.

[5. RV-03: 실제 지연 요청과 늦은 응답 처리]
Task를 반환한다는 이유만으로 비동기 동작이 검증됐다고 판단하지 마.
TaskCompletionSource 등으로 완료·실패·응답 유실·미완료를 통제하는
시험용 IMetaProgressionService를 만들어 실제 UI 흐름을 검사해줘.

요청 처리 상태는 화면의 생명주기와 분리해줘.
화면이 바뀌거나 controller가 disable/enable된 뒤 도착한 이전 요청이
새 화면의 Session·오류·입력 잠금·이동을 덮어쓰지 않아야 해.
정리 코드도 요청/바인딩 소유권을 확인하게 하고, 예전 finally가 새 요청의
Busy 상태를 해제하지 못하게 해줘.

설정 가능한 응답 대기 기준을 두되, 그 시간을 넘겼다는 이유로 처리 실패나
취소 성공을 확정하지 마. '처리 결과 확인 필요' 상태에서 복구 안내와
결과 확인/동일 요청 재시도를 제공해줘. 연출용 10초 watchdog과 구분해줘.

결과가 불명확할 때 requestId·요청 종류·입력 fingerprint·expectedRevision을
보존해줘. 앱 재시작 뒤에도 필요한 미결 요청을 식별하도록 최소한의 기록이나
기존 receipt 조회를 사용하고, 새 요청 ID로 동일 성장/정산/출발을 자동 재실행하지 마.
같은 요청 재시도 시 revision이나 입력을 조용히 바꾸지 마.
처리 여부가 확인되기 전 관련 변경 명령은 막되, 재조회·안내·안전한 복귀 같은
복구 조작까지 무기한 잠그지는 마.

처리 결과를 확인하면 저장된 프로필/런과 UI를 재조정해줘.
필요하면 결과 조회를 위한 작은 계약을 추가하되 실제 Firebase 서비스는 만들지 마.
Unity 메인 스레드에서 .Wait()/.Result로 네트워크 대기를 막거나,
LocalMetaProgressionService 전체를 무조건 Task.Run으로 감싸지 마.

필수 검증:
정상 지연 완료, 확정 전 실패, 확정 후 응답 유실,
미완료 요청의 대기 만료, 같은 요청 재시도, 화면 닫기/재개,
이전 요청의 늦은 성공·실패와 새 바인딩, 앱 재시작 후 미결 요청 확인.
성장 비용·정산 보상·런 생성은 한 번만 적용되어야 해.

[6. RV-04: 누적 저장 비용 측정 후 최소 개선]
검증을 통과하는 신규/100런/1,000런 상당의 프로필 자료를 격리 경로에 준비해줘.
메타 파일 크기, 로비 갱신 1회당 실제 파일 읽기 횟수,
체크포인트 읽기·검증·직렬화·쓰기 시간과 가능한 할당량/프레임 지연을 기록해줘.
단일 측정을 일반화하지 말고 표본 수·환경·빌드 종류·캐시 조건을 보고해줘.

측정에서 중복 읽기나 불필요한 쓰기가 확인되면 같은 화면 갱신에서 읽기 스냅샷을
공유하는 등 작은 변경만 적용하고 동일 조건의 전후 결과를 남겨줘.
실제 변경이 없는 출전 설정 처리도 requestId 중복 계약을 유지해야 해.
캐시는 권위가 아니므로 명령 수락과 저장 직전의 revision 충돌 검사를 생략하지 마.

영수증 단순 삭제, runId/requestId 중복 검사 약화,
전체 파일의 무계획 분리나 DB 교체는 하지 마.
보관·압축 정책은 필요성을 측정해 FOLLOW_UP으로 제시하고,
명확한 병목 근거가 없으면 측정 결과와 현재 구조 유지로 종료해줘.

기존 화면 전체 재생성, 임의 YAML 수정, 공급사 코드 변경은 하지 마.
실제 사용자 저장·백업은 읽기 전용 확인 대상으로만 다루고 복구 시험에 사용하지 마.
Git staging·commit·push·merge·브랜치 변경·reset·stash는 하지 마.
패키지 설치, 글로벌 설정 변경, 외부 서비스/비용 발생은 이번 승인이 아니야.

[8. 검증·진행·반복 상한]
RV-01→RV-02→RV-03→RV-04 순서로 진행하고,
각 단계의 직접 검증이 통과하면 승인된 다음 단계로 진행해줘.
안정화 과정에서 필요한 관련 인터페이스 조정은 한 소유자가 통합해줘.

현재 AGENTS의 검토 상한을 유지해줘. 이 전체 작업은 하나의 Task이며

이미 소진된 승인을 새 Task로 우회하지 마.

초기 개발·TDD에서도 동일 실패의 단순 반복 실행을 하지 말고
재현 조건·원인 가설·변경 근거를 기록해줘.

실제 0건 실행, skipped, inconclusive를 성공 근거로 사용하지 마.
관련 동작이 실제로 바뀐 근거 없이 테스트 삭제·기대값 완화로 통과시키지 마.

Android 모듈이 준비되면 최종 소스의 ARM64 IL2CPP 개발 빌드를 만들고
성공/실패·APK 경로와 해시·경고 종류를 기록해줘.
연결된 승인된 시험 기기가 있으면 실제 사용자 앱/데이터를 덮어쓰지 않는
격리 조건에서 새 출발·주사위 확정·카드·보상·정산·성장 직후의 중단/복귀를 확인해줘.
안전한 설치/실행 조건이 없으면 기기 작업은 보류하고 이유를 적어줘.

필수 Unity 검증이 실행 불가능하면 WAIT_VALIDATION으로 기록하고
검증되지 않은 단계에 의존하는 다음 단계로 완료 처리하며 넘어가지 마.
Android 모듈/기기 부재는 해당 검사만 NOT_RUN으로 분리해줘.
실제로 실행한 검사의 실패는 FAIL이며, 상한 내 미해결 필수 결함은 BLOCKED야.
예산이나 진행 한도에 도달하면 현재 diff·다음 행동·남은 검증·누적 횟수를 기록해줘.
