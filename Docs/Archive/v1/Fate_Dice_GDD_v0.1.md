**2안 기준 / 프로토타입 v0.1 / 2026-09-07**

# 1. 게임의 정체성과 적용 범위

## 1.1 핵심 경험 — 확정 방향

캐릭터 성장이 중심이다. 장비는 현재 전투력을 강화하고, 주사위·운명 조작은 더 좋은 성장 기회와 전투 행동을 얻도록 돕는다. 플레이어가 고민할 것은 복잡한 조작이나 카드 사용 비용이 아니라, **현재 상황에서 어떤 길과 어떤 행동을 선택할 것인가**이다.

핵심 재미는 다음 세 관계에서 만든다.

- **운과 통제:** 처음에는 결과를 받아들이고, 성장하면서 주사위와 운명에 제한적으로 개입한다.
- **현재와 미래:** 당장의 스탯·장비 강화와 앞으로의 성장 효율을 높이는 주사위 투자를 비교한다.
- **선택과 결과:** 노드로 사건의 방향을 고르고, 생성된 카드 중 최종 운명을 선택한다.

캐릭터 성장은 주사위 시스템보다 하위 개념이 아니다. 주사위 투자는 캐릭터가 원활하고 폭발적으로 성장하고 싸우기 위한 중요한 수단이다. 다만 모든 런에서 같은 투자 순서만 정답이 되는지는 플레이 테스트로 확인한다.

## 1.2 플랫폼과 표현 — 확정 방향

Android와 Unity 6.6을 사용하고 모바일 세로 화면으로 고정한다. 플레이어 캐릭터 1명과 적 전투 개체 1개를 기준으로 하며, 파티 조작과 다중 타깃 선택은 초기 범위에서 제외한다.

Unity 공식 릴리스 노트에서 6000.6.0f1은 2026년 8월 31일 공개된 버전으로 확인된다. 프로젝트 목표는 6000.6.x로 기록하고, 실제 사용할 패치와 Firebase SDK 조합은 Android 빌드 시험 후 고정한다. 특정 조합의 호환성을 이 문서만으로 보증하지 않는다. [R1, R14]

화풍, UI 프레임워크, 렌더 파이프라인, 최소 Android 버전, 목표 기기 성능은 아직 확정하지 않는다. 과거 프로젝트의 선택을 이 프로젝트에 자동 승계하지 않는다.

## 1.3 현행안에서 제외된 과거 구상

현재는 주사위 두 개의 A/B/A+B로 이소메트릭 타일을 이동하는 게임이 아니다. 정확 이동거리, 남은 주사위의 탐험력 전환, 통과 타일 효과는 적용하지 않는다. 간단한 가지형 노드는 다시 채택했지만, 주사위는 이동거리가 아니라 **운명·행동 선택지의 확률**을 다룬다.

고등급 운명이 대운명 진척을 자동으로 더 크게 올린다는 규칙도 폐기되었다. 현재는 모든 일반 사건이 +1이다. 전투 행동카드에 공통 MP·행동력·쿨다운을 요구하거나, 별도의 기본 공격 버튼을 항상 제공하는 방식도 적용하지 않는다.

# 2. 런 진행, 노드와 대운명

## 2.1 기본 진행 — 확정 방향

**캐릭터·와일드 카드 선택 → 구간 시작 → 다음 노드 선택 → 6주사위 굴림 → 패·운명력 판정 → 운명카드 생성 → 1장 선택 → 사건 해결·성장 → 대운명 진척 +1 → 다음 노드.**

대운명 도래 후에는 일반 사건 선택을 끝내고 대운명에 도전한다. 돌파 시 현재 구간을 종료하고 다음 구간으로 넘어갈 수 있는 구조를 지향한다. 전체 런의 구간 수와 최종 종료 조건은 아직 미정이다.

## 2.2 노드 선택

**2026-09-10 승인 변경 / 후속 입력 개선:** 새 여정은 시작할 때 층별 폭과 분기 수가 달라지는 전체 절차 지도를 생성한다. 길은 분기·합류하며 선이 교차하지 않고, 모든 노드는 시작점에서 도달해 마지막 단일보스로 이어진다. 플레이어는 연결된 바로 다음 층으로만 이동하며 역행은 허용하지 않는다. 이동 가능한 노드를 누르면 바로 이동하고 별도 이동하기 버튼을 사용하지 않는다. 전투·다른 사건과 보상 처리를 끝내고 돌아오면 현재 완료 노드와 다음 경로가 보이도록 지도를 맞춘다. 이후 수동 지도 스크롤은 유지한다.

지도 전체의 위치·연결은 처음부터 표시하고, 유형은 현재 위치의 다음2층까지 공개한다. 마지막 보스 표식은 항상 보이며 더 먼 일반 노드는 미발견으로 표시한다. 이동 후 접근할 수 없어진 가지는 흐리게 잠긴 상태로 남기고, 선택한 길에서 도달 가능한 합류 노드는 유지한다. 완료 여부와 미선택 가지를 구분하며 좌표·연결·진행 기록을 보존한다.

노드 유형은 전투·이벤트·보물·상점·휴식의 5종이다. 노드의 역할은 만날 사건의 방향을 선택하는 것이다. 예를 들어 휴식 노드를 선택하면 카드 중 최소 1장의 휴식을 보장한다.

노드 유형은 후보 한 장의 유형 보장과 나머지 후보의 유형 편향에 사용하며 사건 자체를 강제하지 않는다. 신규 생성 모드1은 전체 절차 지도를 사용하고, 기존 저장의 모드0은 원래 분기 수·앞길 보충 규칙으로 이어한다. 새 지도용 난수는 게임 주사위 난수와 분리하며 저장된 생성 버전·설정·시드로 같은 지도를 재현한다.

## 2.3 턴과 진척

**일반 운명 사건 하나 해결 = 탐험 턴 1회 = 대운명 진척 +1.** 전투 안에서 여러 번 주사위를 굴리거나 공격해도 탐험 진척이 추가로 늘어나지 않는다. 확률 조작과 화면 재진입도 별도 탐험 턴으로 세지 않는다.

대운명까지 거치는 일반 사건 수는 설정 데이터로 관리한다. 현재 검토 범위는 10~20회이며, 고정 하드코딩하지 않는다. 최초 통합 테스트는 10회로 시작하는 것을 제안한다. 한 사건을 재전송·재개했다고 진척이 중복 증가해서는 안 된다.

## 2.4 대운명 강제 조우

**2026-09-10 승인 변경:** 신규 지도는 설정된 일반층 수를 모두 지난 뒤 **미리 생성된 단일 대운명 노드로 합류한다.** 기본은 일반10층과 11층의 보스이며, 어떤 경로를 선택해도 일반 사건10회를 해결한다. 일반층 수는 설정으로 관리한다. 현재 사건과 보상을 마친 후 다음 층으로 진행하고, 임계점 도달 때 기존 일반 노드를 일괄 보스로 바꾸지 않는다. 남은 일반층 수는 화면에 보여준다.

기존 저장의 생성 모드0은 당시의 임계점 이후 노드 전환 규칙을 유지한다. 신규 모드1의 여러 보스 선택은 이번 범위에 포함하지 않는다. 보스 승리 후 결과 화면으로 종료하는 기존 1구간 흐름을 유지하며, 보스 해결은 일반 사건 진척에 추가로 세지 않는다.

**보류:** 특수 던전에서 진척을 멈추는 규칙, 사건별 진척 가속·지연, 다중 구간과 무한 도전은 후속 확장이다.

# 3. 주사위, 패와 운명력

## 3.1 기본 규칙 — 확정 방향

기본 주사위는 6면체 6개다. 결과의 합계보다 동일 숫자 묶음과 연속 숫자 조합이 중요하다. 성립한 패 중 우선순위가 가장 높은 패를 자동으로 판정하며, 플레이어가 패를 따로 선택하지 않는다.

| 패 ID 예시 | 패 이름 | 성립 조건 | 예시 |
|---|---|---|---|
| Pair | 원 페어 | 같은 숫자 2개 이상 | 1 1 2 3 4 6 |
| TwoPairs | 투 페어 | 서로 다른 숫자 두 종류가 각각 2개 이상 | 1 1 3 3 5 6 |
| Triple | 트리플 | 같은 숫자 3개 이상 | 1 1 1 2 4 6 |
| ThreePairs | 트리플 페어 | 서로 다른 숫자 세 종류가 각각 2개 | 1 1 3 3 6 6 |
| FullHouse | 풀하우스 | 한 숫자 3개 이상 + 다른 숫자 2개 이상 | 2 2 2 5 5 6 |
| FourKind | 포카드 | 같은 숫자 4개 이상 | 4 4 4 4 2 6 |
| Straight | 스트레이트 | 서로 다른 연속 숫자 5개 이상 | 1 2 3 4 5 5 |
| FullStraight | 풀 스트레이트 | 1~6을 모두 포함 | 1 2 3 4 5 6 |
| FiveKind | 파이브 카드 | 같은 숫자 5개 이상 | 5 5 5 5 5 2 |
| SixKind | 식스 카드 | 같은 숫자 6개 | 3 3 3 3 3 3 |

**표의 순서는 최종 서열이 아니다.** 4연속 스트레이트는 사용하지 않는다. 더블 트리플은 별도 패 없이 풀하우스 조건에 포함하는 안을 유지한다. 하나의 숫자 묶음을 서로 다른 두 페어로 중복 계산하지 않는다.

기본 6D6에서는 전부 다른 결과가 1~6 풀 스트레이트이고, 그렇지 않으면 최소 원 페어가 존재한다. 따라서 기본 규칙에는 무패가 필요 없다. 향후 특수 기호 면을 추가하면 별도 판정 규칙이 필요하다.

## 3.2 데이터 연결

**주사위 결과 → 최고 패 → 기본 운명력 1~N → 성장 보정 → 최종 운명력 → 목적별 등급 확률표.** 패 이름에 운명 등급 확률을 직접 하드코딩하지 않는다. 탐험용과 전투용 확률표는 분리한다.

**프로토타입 제안:** 최고 패 선택용 우선순위와 보상용 기본 운명력은 별도 필드로 둔다. 처음에는 같은 순서를 사용하더라도, 확률표를 조정하다 패 판정까지 의도치 않게 바뀌지 않도록 한다. 특정 패 보너스가 최고 패 선택 자체를 바꾸는지는 후속 규칙으로 남긴다.

## 3.3 시뮬레이션

균등한 기본 6D6의 순서 있는 결과는 6⁶ = 46,656개다. 기준 검증은 전체 경우를 열거해 각 패의 단독 성립 빈도와 최고 패 판정 후 빈도를 분리 집계할 수 있다. 우선순위를 바꾸면 최종 판정 빈도도 달라진다.

특수 주사위 분포·재굴림 정책·성장 효과가 추가된 경우 별도 테스트를 한다. 이 문서에는 시뮬레이션 결과나 최종 패 서열을 확정하지 않았다.

# 4. 운명카드 생성과 등급

## 4.1 카드별 독립 등급 — 확정 방향

운명 등급은 **일반 / 고급 / 희귀 / 영웅 / 전설**의 5단계다. 카드마다 동일한 최종 운명력에 대응하는 확률표를 참조해 등급을 개별 추첨한다. 기본 제시 수는 3장을 시험하되 설정값으로 관리한다.

낮은 운명력에서도 상위 등급이 나올 여지를 두고, 높은 운명력일수록 상위 등급의 출현 가능성이 유의미하게 커지도록 조정한다. 단, 사용자가 설정한 운명 등급 상한 밖의 카드는 나오지 않아야 한다. 좋은 패가 세 장 모두의 고등급을 보장하지는 않는다.

높은 운명 등급은 더 많은 보상과 영향력 있는 성장 요소를 얻을 기회를 뜻한다. 평균적인 위험도는 다소 높아질 수 있으나, 높은 등급의 모든 사건이 무조건 더 위험한 것은 아니다. 보물·휴식과 전투의 위험 성격을 구분한다.

**상점 프로토타입 조정(2026-09-11):** 같은 상품의 고등급 가격이 더 비싸지 않도록 새 여정의 일반/고급/희귀/영웅/전설 배율을 1/.95/.9/.85/.8로 시험한다. 최종 밸런스 확정값이 아닌 조정 가능한 초기값이다. 정수 가격 계산은 기존 방식을 유지하므로 인접 등급의 가격이 같을 수 있다. 상품·보상은 그대로이며 기존 여정은 저장된 규칙과 입장 시 확정한 가격을 유지한다.

## 4.2 유형 생성 — 확정 방향

선택한 노드 유형과 동일한 카드 **1장을 확정 생성**하고, 나머지 2장은 해당 유형에 편향된 가중치로 생성한다. 확정은 유형을 보장하는 것이며, 등급까지 고정하는 것은 아니다.

같은 유형의 카드가 여러 장 나오는 것을 허용한다. 전투 노드에서 전투 3장이 나올 수도 있다. 운명카드의 동일 사건 ID까지 중복할지와 동일한 표시 카드가 나왔을 때의 UX는 추후 조정한다.

**생성 예시:** 보물 노드 → 보물 1장 확정 + 나머지 유형 추첨 → 각 카드의 등급 추첨 → ‘일반 보물 / 희귀 전투 / 전설 보물’. 유형과 등급을 독립적으로 다룬 뒤 해당 조합의 실제 사건 풀에서 내용을 선택한다.

## 4.3 정보 공개 — 확정 방향

선택 전 기본 공개 정보는 **유형과 등급만**이다. 구체적인 적 계열·위험도·보상·상점 품목·사건 이름은 기본적으로 숨긴다. 캐릭터 능력이나 특성에 따라 몬스터 계열·대략적 위험도 같은 추가 정보가 공개될 수 있다.

정보 해금이 단계형인지 확률형인지는 미정이다. 프로토타입에서는 기본 정보만 표시한다. 전투에 실제로 들어간 뒤에는 적의 다음 행동을 공개하므로, 탐험 단계의 정보 은닉과 모순되지 않는다.

**프로토타입 제안:** 실제 사건 내용은 카드 생성 시 함께 정하고 숨긴다. 선택 후 재추첨하지 않아야 나중에 추가 정보를 공개하거나 재개·검증할 때 결과가 바뀌지 않는다.

## 4.4 고등급 수용 제한

플레이어가 등장 가능한 최대 운명 등급을 제한할 수 있는 방향을 채택한다. 수치 보상 보너스와 연결하되 적용 시점·배율은 미정이다. 고등급 허용 시 추가 수치 보상을 주고 구간 시작에 설정을 고정하는 방식은 제안 단계다.

상한 초과 확률의 재분배, 허용 구간의 확률 합이 0일 때 처리, 대운명에 대한 상한 적용은 구현 전에 정의한다. 탐험 운명 제한을 전투 행동카드에 자동 적용하지 않는다. **등급에 관계없이 사건 해결 진척은 +1이다.**

# 5. 전투와 행동카드

## 5.1 기본 전투 — 확정 방향

플레이어 1명 대 적 전투 개체 1개로 진행한다. 적의 다음 행동을 확인한 뒤 6주사위를 굴리고, 생성된 행동카드 중 하나를 선택하면 즉시 실행한다. 이후 살아 있는 적이 예고한 행동을 수행한다.

**적 행동 예고 → 주사위·제한적 조작 → 최고 패·운명력 → 슬롯별 등급 추첨 → 행동카드 제시 → 1장 실행 → 승패 확인 → 적 행동 → 승패 확인 → 다음 전투 턴.**

모든 제시 행동카드는 비용·쿨다운·장비 조건 때문에 비활성화되지 않고 즉시 사용할 수 있어야 한다. 기본 공통 MP·행동력은 없고, 카드 밖의 상시 기본 공격 버튼도 두지 않는다. 조건은 사용 허가가 아니라 추가 효과의 조건으로 설계한다.

## 5.2 행동 풀과 와일드 카드

캐릭터마다 기본 행동카드 풀을 가진다. 계정에 영구 보유한 카드 중 1장을 와일드 카드로 추가할 수 있으며, 등장 확률 우대나 출현 보장은 없다. 시작 풀의 최종 장수와 최대 장수 제한은 확정하지 않는다.

등급별로 별도 행동카드군을 두는 것이 기본이다. 모든 카드를 등급별 5종으로 복제하는 구조는 아니지만, 개별 카드의 상위 변형은 허용한다. 카드 제시 시 중복을 허용하며, 공격·방어 역할을 매번 강제로 보장하지 않는다.

기본 시작 풀에는 영웅·전설 고유 카드를 넣지 않는다. 영구 보유한 고등급 와일드 카드를 시작 시 허용할지는 별도 결정 사항이다. 프로토타입 와일드 카드는 희귀 이하의 시험 카드로 제한하는 안을 제안한다.

## 5.3 비어 있는 등급의 대체 생성

슬롯 등급에 맞는 보유 카드가 있으면 해당 풀에서 뽑는다. 없다면 보유 행동카드 중 무작위로 하나를 뽑아 슬롯 등급에 맞게 임시 보정한다. 원본 카드의 소유 등급·영구 능력은 변경하지 않는다.

강화는 기존 피해량·보호량·기존 효과의 수치 중심이다. 단순 등급 보정만으로 원본에 없던 출혈·관통 같은 새 메커니즘을 자동 추가하지 않는다. 고등급 고유 카드의 획득 가치는 별도로 남긴다.

**주의:** 나중에 저등급 카드 삭제로 빈 등급이 생기고, 대체로 고등급 원본이 뽑힐 경우에는 감쇠·보정 규칙을 별도 확정해야 한다. 모든 카드 삭제로 행동 풀이 비는 경우도 출시 전 처리해야 한다. 프로토타입은 스킬 삭제를 제외하고 기초 등급 풀을 유지한다.

## 5.4 최소 전투 콘텐츠

플레이어는 **공격 / 방어 / 강공격 / 희귀 행동 1종**, 적은 **공격 / 방어 / 강공격**만 사용한다. 구체적인 카드 값과 희귀 행동의 정체는 임시 데이터로 시작한다.

캐릭터 고유 스택·게이지는 향후 허용하되, 부족하다는 이유로 제시된 카드를 사용 불가로 만들지 않는다. 광란 자동 선택 같은 예외는 아직 개별 컨셉 후보이며 공통 전투 규칙으로 도입하지 않는다.

# 6. 캐릭터 성장과 장비

## 6.1 기본 스탯과 혼합 성장 — 확정 방향

| 기본 스탯 | 역할 |
|---|---|
| 최대 HP | 생존 한계. 현재 HP는 별도 런 상태로 기록 |
| 위력 | 공격 행동의 피해 스케일링 |
| 수호 | 방어 행동의 보호량 스케일링 |

수호를 상시 받는 피해 감소와 같은 의미로 섞지 않는다. 치명타·회피·명중·속도·속성 저항 등은 초기 공통 스탯에서 제외한다.

성장은 혼합형이다. 경험치·레벨업은 기본 스탯을 성장시키고, 운명 보상은 행동카드·장비·주사위·운명 조작 등 빌드를 성장시킨다. 레벨업은 캐릭터별 성장표로 자동 처리하는 프로토타입 안을 사용한다. HP 증가 시 현재 HP도 회복할지는 별도 수치 규칙으로 정한다.

## 6.2 장비 3슬롯 — 확정 방향

| 슬롯 | 주 역할 | 효과 예시 |
|---|---|---|
| 무기 | 위력·공격 행동 강화 | 위력 증가, 특정 태그 피해 강화 |
| 방어구 | HP·수호·생존 강화 | 수호 증가, 방어 행동 보호량 강화 |
| 장신구 | 특수 규칙과 확률 조작 | 특정 패·주사위·운명 정보 효과 |

**프로토타입 제안:** 장비는 고정된 기본 스탯과 짧은 고유 효과 중심으로 만든다. 복잡한 랜덤 옵션, 다수 장비 보관, 제작·강화는 제외한다. 획득 시 현재 장비와 비교해 교체하거나 포기하는 정도로 시작한다.

장비 등급을 운명과 같은 5단계로 사용할지는 장비 상세 기획에서 확정한다. 장비가 행동카드를 추가하는 기능도 확장 후보이며, 초기 장비의 필수 기능으로 간주하지 않는다.

## 6.3 주사위·운명 투자

주사위 투자는 탐험뿐 아니라 전투 행동의 확률에도 영향을 준다. 캐릭터의 현재 전투력과 앞으로의 성장 효율이 함께 개선될 수 있으므로, 탐험용 확률표와 전투용 확률표를 독립 조정한다.

초기에는 나온 결과를 받아들이는 것이 기본이다. 런 중 또는 향후 시작 특성으로 재굴림·숫자 보정·특수 주사위·패 운명력 보너스 등을 얻을 수 있다. **프로토타입에서는 주사위 1개 교체와 획득형 재굴림 하나를 시험 기능으로 제안한다.** 공용 조작권의 사용량·회복 시점은 별도 설정한다.

## 6.4 영구 데이터와 런 데이터

영구 보유 와일드 카드 등 해금 정보는 계정 데이터다. 런 중 레벨·HP·장비·행동 풀·임시 주사위 강화는 런 상태로 구분한다. 런 종료 후 무엇을 영구 보상으로 전환할지와 영구 스탯 성장 허용 여부는 아직 정하지 않았다.

# 7. 태그와 효과 시너지

## 7.1 적용 방향 — 확정

장비와 행동카드에 여러 태그를 부여한다. 효과는 태그를 참조하여 적용 대상·강화·조건을 결정할 수 있다. 예를 들어 화염구는 **불 / 마법 / 투사체** 태그를 가진다.

**설계 제안:** 태그는 분류 정보로 두고 실제 효과와 분리한다. ‘불’ 태그만으로 화상이 자동 부여되지는 않는다. 화상은 카드나 장비의 명시적인 효과여야 한다. 장비의 ‘불’ 태그가 장착자의 모든 행동에 자동 전이되지도 않는다.

## 7.2 최소 조건 표현

| 조건 | 의미 | 예시 |
|---|---|---|
| ANY | 지정 태그 중 하나 이상 포함 | 불 또는 번개 행동 |
| ALL | 지정 태그를 모두 포함 | 불이면서 마법인 행동 |
| NONE | 지정 태그를 하나도 포함하지 않음 | 마법이 아닌 행동 |

조건을 평가할 대상도 명시한다. 행동카드의 태그를 읽는지, 장착 장비의 태그를 읽는지 섞지 않는다. ‘불 장비 2개’는 태그 존재 검사와 달리 장착 개수 조건이 필요하므로 확장 규칙으로 둔다.

태그 이름은 표시명과 내부 식별자를 분리한다. 카테고리 구분은 정리용이며, 초기부터 상속·포괄 일치·자유 스크립트 조건을 모두 구현하지 않는다.

## 7.3 효과는 바꾸는 값을 분명히 지정

‘불 행동 효과 +20%’처럼 피해·보호막·회복·지속시간 모두에 적용되는지 불명확한 문구는 피한다. 예를 들어 **‘불 태그 행동이 주는 피해 +20%’**로 명시한다.

| 카드 | 장비 효과 | 적용 결과 |
|---|---|---|
| 화염구: 불·마법·투사체·공격 | 불 태그 행동 피해 증가 | 피해에 적용 |
| 화염구: 불·마법·투사체·공격 | ALL(마법, 투사체) 피해 증가 | 피해에 적용 |
| 방어: 방어 | 불 태그 행동 피해 증가 | 적용 안 됨 |

동일 효과의 중첩·덧셈·곱셈 순서와 반올림은 공통 계산 규칙으로 결정한다. UI 표시와 실제 결과, 향후 서버 검증이 같은 규칙을 사용해야 한다.

## 7.4 프로토타입 범위

카드·장비의 태그 보유, 조건 일치, 피해 또는 보호량 강화만 우선 검증한다. 행동 생성 가중치 변경·태그 전파·연쇄 발동·상태이상 상성은 확장 후보로 남긴다. UI에는 핵심 태그만 짧게 표시하고 상세 설명에서 전체를 확인하도록 제안한다.

# 8. 세로 UI, 저장과 결과

## 8.1 UI 원칙 — 확정 방향

세로 고정과 간단한 조작을 우선한다. 기본 흐름은 **주사위 → 선택지 → 한 장 선택**이다. **2026-09-10 승인 변경:** 탐험 운명카드는 지도 위 별도 팝업에서 탭으로 강조하고, 팝업 하단 ‘선택’ 버튼으로 확정한다. 전투 행동카드는 기존처럼 한 장 선택 시 즉시 행동하며, 추가 확인창을 더 열지 않는다.

캠페인 지도는 어두운 판타지 스타일의 원형 노드·점선 연결·파란 현재 위치 표식으로 구성한다. 상단 진행 정보, 세로 스크롤 지도와 접을 수 있는 범례, 하단 노드 상세·이동 버튼과 플레이어 상태를 구분한다. 운명 팝업은 기본 카드3장이 함께 보이도록 배치하며 더 많은 후보는 가로 스크롤한다. 주사위6개는 한 줄로 표시한다. 서로 다른 세로 비율과 실제 Android 기기의 판독성·터치 검증은 구현 검증과 구분해 기록한다.

탐험 카드에는 유형·등급과 유형의 일반적인 설명만 표시하고, 선택 전 구체 적·보상·위험도는 공개하지 않는다. **전투 행동카드에는 실행 효과를 읽을 수 있게 표시한다.** 탐험 정보 은닉 규칙을 행동 설명까지 확장하지 않는다. 적 HP·현재 보호막·다음 행동과 내 HP를 구별해 보여준다.

운명 팝업을 닫거나 뒤로 가도 확정된 노드·후보·난수·저장은 유지하며 지도에서 같은 선택 창을 다시 열 수 있다. 재굴림은 기존 비용과 후보 재생성 규칙을 유지하고 강조 선택을 해제한다. 선택 대기는 연출 제한 시간에 포함하지 않는다. 확정 성공 후 선택 효과와 팝업 퇴장이 실제로 끝나면 사건을 표시하며, 연출은 기존 실시간10초 강제 종료·로그 규칙으로 감독한다.

## 8.2 연출과 조작

탐험 주사위는 기대감, 전투 주사위는 반복 속도를 우선한다. 자동 패 판정과 카드 생성을 불필요한 버튼으로 나누지 않는다. 재굴림 능력이 없으면 곧바로 카드 선택으로 진행할 수 있어야 한다.

**후속 사용자 승인:** 첫 전투 진입은 전투 화면과 적을 보여주는 짧은 등장 연출이 끝난 뒤 주사위 창을 연다. 다음 턴과 재굴림에서는 진입 연출을 반복하지 않는다. 전투 주사위를 굴리기 전 저장을 재개하면 진입 연출 후 미굴림 창을 열고, 이미 결정된 행동 카드 저장은 그대로 재개한다. 실제 연출 종료를 기다리며 기존 실시간10초 오류 복구를 유지한다.

좋은 패 연출을 보여줬더라도 카드별 추첨으로 최상위 등급이 안 나올 수 있다. 따라서 패 성공 연출과 실제 카드 등급 연출을 구분하고, 아직 결정되지 않은 전설 보상을 먼저 약속하는 표현은 사용하지 않는다.

## 8.3 저장·중단 복귀 — 프로토타입 제안

저장은 노드 선택, 주사위 결과 확정, 카드 선택, 사건 해결, 보상 적용을 구분한다. 최소한 현재 상태·주사위 결과·제시된 카드 ID와 등급·난수 상태·처리된 보상 ID·설정 버전을 보존한다.

앱을 닫고 다시 열어 같은 순간의 주사위나 카드가 새로 뽑히지 않게 한다. 연출 스킵은 결과를 바꾸지 않는다. 전투 승리와 보상 지급 사이에 종료되어도 보상이 사라지거나 두 번 들어오지 않도록 설계한다.

이 저장 방식은 재현성과 정상 복귀를 위한 것이며, 악의적으로 조작된 단말의 상태가 참임을 증명하지는 않는다. 서버와의 신뢰 경계는 10~12장에서 별도로 다룬다.

## 8.4 점수와 스피드런

클리어·고득점 목표는 유지한다. 다만 현재는 일반 사건마다 +1이고 구간 임계값이 같으므로, **탐험 턴 수 자체가 모든 정상 경로에서 같아질 수 있다.** 고등급 자동 가속은 다시 도입하지 않는다.

프로토타입에서는 클리어 여부·탐험 사건 수·전투 턴 수·선택 등급·플레이 시간을 기록한다. 스피드런 보너스는 전투 턴 기준인지, 추후 사건별 가속을 사용할지 결정한 뒤 산식을 도입한다. 조작 속도를 강요하는 실시간 보너스는 확정하지 않는다.

# 9. 구현 데이터와 계산 경계

## 9.1 데이터 기반 설정 — 설계 제안

패 서열·운명력·확률·카드 수·대운명 임계값·성장표를 코드의 고정 숫자로 만들지 않는다. 다만 데이터화가 무제한 범용 엔진 구현을 뜻하지는 않는다. 현재 기획에서 쓰는 규칙만 구현한다.

| 데이터 묶음 | 핵심 내용 |
|---|---|
| 주사위 | 안정적인 ID, 6개 면, 면별 값·가중치, 임시 변경 상태 |
| 패 | ID, 판정 조건, 우선순위, 기본 운명력 |
| 등급 확률 | 탐험/전투 구분, 운명력별 5등급 가중치 |
| 노드 | ID, 연결, 유형, 보장 유형, 편향 가중치 |
| 운명 사건 | 유형, 등급, 숨김 정보, 실제 사건·보상 ID |
| 행동카드 | 원본 ID·등급, 태그, 피해·보호 효과, 임시 슬롯 등급 |
| 캐릭터·장비 | 기본 스탯, 성장표, 행동 풀, 슬롯, 태그 효과 |
| 런 | 현재 상태, 진척, 소유물, 처리 기록, 설정 버전, 난수 상태 |

## 9.2 게임 규칙과 화면 분리

주사위 결과·패 판정·확률 추첨·카드 생성·피해·성장 계산은 화면과 애니메이션 밖의 규칙으로 분리한다. Unity 화면은 결정된 결과를 표시하고 사용자 선택을 전달한다.

랜덤 결과는 하나의 관리 지점에서 받되, 탐험·전투·연출의 난수 흐름을 구분하는 것을 제안한다. 화면 효과의 랜덤 호출이 실제 운명 결과를 바꾸면 안 된다. 런 중에는 규칙·확률표 버전을 고정하고 변경된 데이터는 새 런부터 적용한다.

## 9.3 구현 착수 전에 필요한 작은 규칙

큰 기획을 다시 열 필요는 없지만 다음 항목에는 임시 실행값이 필요하다.

- **피해·보호막:** 스탯 계수, 등급 보정, 태그 보정, 반올림·최솟값·만료 시점.
- **추첨:** 임시 패 우선순위, 확률 합계 검증, 범위 밖 운명력, 비어 있는 카드·사건 풀 처리.
- **보상:** 경험치·레벨 표, HP 증가 시 현재 HP 처리, 장비 교체·재굴림 획득량.

**보호막 기본안:** 획득 즉시 유효하며 다음 상대 행동 처리가 끝난 뒤 남은 양이 만료된다. 이 경우 적의 방어 행동으로 생긴 보호막은 다음 플레이어 행동까지 유지된다. 이는 구현용 제안이며, 수호 스탯 자체의 효과와 혼동하지 않는다.

## 9.4 서버 준비형 구조

로컬 규칙 결과가 곧바로 서버 영구 데이터 쓰기로 이어지지 않게 한다. 로컬 저장, 계정 인증, 서버 체크포인트·정산은 별도 경계로 둔다. 최초 루프는 로컬 시험 계정으로 실행할 수 있지만, 실제 계정의 영구 해금·재화·공인 결과는 별도 서버 승인 경로를 거치도록 준비한다.

Unity의 C# 규칙을 Firebase Functions에 그대로 실행할 수 있다고 가정하지 않는다. 별도 서버 런타임으로 일부 규칙을 재현한다면 난수·정수 계산·정렬·반올림에 대한 동일 테스트 벡터를 사용해야 한다. [R7]

# 10. Firebase와 보안의 역할

## 10.1 목표와 한계

**사용자 기술 방향:** Firebase 기반의 제한적인 서버 검증과 Google 로그인 인증을 사용한다. 모든 주사위·전투를 실시간 서버에서 실행하는 구조는 목표가 아니다. 긴 런 전체를 서버가 매 턴 계산·저장하지 않도록 비용을 통제한다.

**보안 목표는 ‘완전한 치트 방지’가 아니라 계정 접근, 비정상 요청, 영구 데이터 변조, 중복 보상 및 명백한 불가능 결과의 억제다.** 로컬 메모리 조작이나 그럴듯하게 위조한 전투 결과는 제한적 검증만으로 모두 판별할 수 없다.

## 10.2 권장 보안 구성

| 구성 | 맡기는 역할 | 보장하지 않는 것 |
|---|---|---|
| Google 로그인 + Firebase Authentication | 사용자를 Firebase 계정으로 인증 | 플레이 결과의 정당성 |
| Firebase App Check + Play Integrity | 앱·실행 환경 증명을 활용한 요청 검증 | 모든 단말 치트 탐지 |
| Cloud Firestore Security Rules | 클라이언트의 데이터 읽기·쓰기 권한 제한 | 전투 규칙의 전체 검증 |
| Cloud Functions | 중요한 요청의 검증·보상 계산·정산 | 구현하지 않은 게임 규칙 검증 |
| Firestore 트랜잭션 | 보상 처리 상태와 영구 데이터의 원자적 갱신 | 중복 의미를 자동 판단하는 게임 로직 |

Firebase는 Authentication과 App Check를 서로 다른 보안 계층으로 설명하며, App Check 역시 모든 악용을 제거한다고 보장하지 않는다. Unity App Check는 Android용 Play Integrity 공급자를 지원한다. [R2–R5]

## 10.3 서버가 최종 권위를 가지는 데이터 — 권장안

계정의 영구 카드 소유권, 영구 해금, 영구 재화가 도입될 경우 그 잔액, 서버 인정 보상, 제출된 결과의 승인 상태는 서버가 확정한다. 시작 시 와일드 카드 소유 여부도 서버 보유 정보를 기준으로 확인한다.

클라이언트에는 자신의 허용된 계정 정보를 읽고 요청을 보내는 권한을 주되, 영구 잔액·소유권·공인 점수를 직접 덮어쓰게 하지 않는다. 본인 UID라는 이유만으로 중요한 계정 문서의 임의 쓰기를 허용하지 않는다. Firestore 서버 라이브러리는 Security Rules를 우회하므로 서버 함수에서 인증·권한·입력을 별도로 검증하고 IAM을 제한한다. [R8]

런 내부 HP·카드 선택·장비와 주사위 변화는 로컬에서 반응하고, 서버에는 설정한 지점에서 검증 자료를 제출한다. 로컬 골드와 영구 재화는 다른 데이터로 취급한다. 서버에 ‘골드 1,000 추가’를 요청하는 대신 사건·보상 식별자를 보내고 서버 규칙으로 지급량을 계산하도록 한다.

# 11. 제한적 검증과 정산 흐름

## 11.1 검증 경계 — 권장안

서버 호출은 **런 시작 / 구간 체크포인트 / 대운명 진입·결과 / 런 최종 정산 / 영구 데이터 변경**에 집중한다. 일반 전투의 주사위 버튼마다 서버 응답을 기다리게 만들지 않는다. 최종 결과 하나만 전송하는 방식도 기본안으로 삼지 않는다.

체크포인트 간격은 사건 수 기반 설정으로 둔다. 예를 들어 5개 사건마다 제출할 수 있으나 확정 수치는 아니다. 구간·보스 같은 앵커를 우선하고, 긴 세션의 시간 기반 보조 간격은 실제 런 길이에 맞춰 결정한다.

## 11.2 한 런의 서버 처리

| 시점 | 클라이언트 요청 | 서버 처리 |
|---|---|---|
| 런 시작 | 캐릭터·와일드 카드·운명 상한 선택 | 소유권 확인, runId·시작 상태·규칙 버전 확정 |
| 체크포인트 | 이전 승인 ID, 증가하는 순번, 선택·변경 기록, 현재 상태 | 연속성·자원 사용·보상 출처·진척 규칙 점검 |
| 대운명 진입 | 현재 구간·진척·보스 식별자 | 해당 보스 진입 자격 확인 |
| 대운명 결과 | 결과 요약, 필요한 행동 기록 | 검증 범위에 따라 수락·보류·거절 |
| 최종 정산 | runId와 정산 요청 ID | 허용된 보상을 서버 계산하여 한 번만 지급 |

보상 ID·요청 ID를 이용해 같은 요청이 재전송되면 기존 결과를 돌려준다. ‘처리 완료’ 기록과 계정 보상은 하나의 트랜잭션으로 갱신하는 방식을 제안한다. Firestore의 원자적 처리 기능을 활용할 수 있으나, 어떤 요청을 같은 것으로 판단할지는 애플리케이션이 정해야 한다. [R9]

## 11.3 무엇을 검증했는지 구분

**기본 검증:** 인증된 UID·runId 소유권, 규칙 버전, 순서, 소유 카드·장비, 비용·보상 중복, 진척 범위와 가능한 스탯 범위를 검사한다. 이것은 불가능하거나 일관성이 없는 결과를 걸러내는 수준이다.

**추가 검증 후보:** 서버가 발급한 구간 난수 조건과 선택 기록으로 주사위·카드·보상 후보를 재생성한다. 실행 순서와 난수 소비가 일치해야 하며, 카드가 합법적으로 나왔다는 사실만으로 전투 승리가 증명되는 것은 아니다.

**중요 결과 검증 후보:** 대운명·고가치 보상·비정상 기록에 한해 전투 행동 로그를 재연하거나 더 강하게 검사한다. 재연하지 않은 전투의 정당성은 일부 신뢰로 남는다. 어느 결과까지 재연할지는 성능·비용 시험 후 결정한다.

로컬 스냅샷·해시·서명된 세션 ID만으로 내부 플레이의 정당성이 증명되지는 않는다. 서버 발급 시드도 단독 치트 방지 장치가 아니며, 공개된 시드로 미래 결과를 예측하는 위험까지 별도 검토해야 한다.

## 11.4 오프라인과 장애

통신 실패 시 진행을 즉시 삭제하지 않고 저장·재시도를 제공하는 방향을 권장한다. 다만 미승인 결과가 영구 재화·해금·공인 점수에 바로 반영되어서는 안 된다. 개발용 로컬 런과 서버 승인 런은 구분한다.

오프라인 시작 허용, 승인 전 진행 한도, 복수 기기 동시 런, 충돌 복구 정책은 출시 전 결정한다. App Check 실패 하나만으로 자동 영구 제재하지 않고 보류·재인증·재시도와 실제 악성 징후를 구분한다.

# 12. 인증·배포와 운영 검증

## 12.1 Google 로그인 연결

**권장 흐름:** Android의 지원되는 Google 로그인 방식으로 Google ID 토큰 획득 → Firebase 인증 자격 증명으로 교환 → Firebase 계정 세션 생성 → 서버는 Firebase ID 토큰을 검증해 UID 식별.

Google ID 토큰과 Firebase ID 토큰을 혼동하지 않는다. 서버는 요청 본문의 UID·이메일을 인증 근거로 사용하지 않는다. Firebase Unity 공식 문서도 Google 로그인 토큰을 Firebase 자격 증명으로 변환하는 흐름을 제시한다. [R2]

Android의 기존 Google Sign-In API는 폐기 예정·이전 대상이므로 Credential Manager 기반 연결을 우선 검토한다. Unity에서 사용할 플러그인 또는 네이티브 브리지는 별도 선정하고 Android 실기기에서 확인한다. 오래된 로그인 플러그인을 검증 없이 채택하지 않는다. [R3]

## 12.2 App Check와 권한

Unity에서 App Check를 초기화하는 것만으로 서버가 미검증 요청을 거절하는 것은 아니다. 보호 대상 Firestore와 callable 함수에서 각각 강제 검증을 적용해야 한다. callable SDK는 사용 가능한 인증·App Check 토큰을 전달하지만, 서버 함수는 로그인 존재와 해당 요청의 권한을 명시적으로 확인해야 한다. [R5–R7]

개발·테스트·운영 환경을 분리한다. 개발용 Debug 공급자·토큰을 운영 경로에 사용하지 않는다. 배포 서명·앱 등록·Play Integrity 정책을 맞추고, Google Play 내부 테스트 빌드로 정상 기기와 실패 케이스를 확인한 뒤 강제 적용한다.

서비스 계정 비밀키나 서버용 서명 비밀키를 Unity 앱에 포함하지 않는다. Firebase의 일반 클라이언트 설정 파일·API 키를 숨기는 것만으로 접근 권한이 보호되는 것도 아니다. [R10, R14]

## 12.3 비용과 응답성

Cloud Functions 배포에는 Blaze 요금제 구성이 필요하므로 Firebase를 사용하면 운영 비용이 0이라고 가정하지 않는다. [R11]

런당 호출 수, 체크포인트 크기, 함수 실행 시간, Firestore 읽기·쓰기 수, 로그 보존량을 측정한다. 인증된 사용자도 과도한 요청을 보낼 수 있으므로 사용자·런 단위 요청 제한과 검증 비용 상한을 둔다. 단순 예산 알림만으로 비용이 자동 차단된다고 가정하지 않는다. [R12]

App Check 토큰은 SDK의 갱신·캐시 정책을 활용하고, 주사위마다 무결성 증명을 새로 요구하지 않는다. 증명 빈도는 지연·보안·할당량의 절충이므로 실측 후 조정한다. [R5]

## 12.4 초기에 확인할 연동 결과

Unity 6.6 Android 빌드 실행, Google 로그인 성공·취소·만료, Firebase 로그인 연결, App Check 성공·거절, 보호된 서버 함수 호출, 중요 문서 직접 쓰기 거절, 같은 정산 요청의 중복 지급 방지를 확인한다. 문서 작성 시점에는 어느 항목도 실제 실행 검증 완료로 표시하지 않는다.

# 13. 프로토타입 범위와 구현 순서

## 13.1 최소 콘텐츠

| 항목 | 초기 범위 |
|---|---|
| 플랫폼·화면 | Android, 세로 고정 |
| 캐릭터 | 1명, HP·위력·수호 |
| 행동카드 | 공격·방어·강공격·희귀 행동 1종 |
| 적 | 공격·방어·강공격을 사용하는 일반 적과 보스 |
| 탐험 | 5유형 노드, 1장 유형 확정 + 나머지 편향 |
| 주사위 | 기본 6D6, 10패, 설정형 운명력·확률표 |
| 성장 | 경험치·레벨업, 최소 장비·주사위 보상 |
| 장비·태그 | 3슬롯, 태그 조건 피해·보호량 효과 시험 |
| 대운명 | 일반 사건 10~20회 설정, 최초 시험 10회·보스 1회 제안 |
| 저장·서버 | 로컬 복귀 + 별도 Firebase 연동·정산 시험 |

노드 미리보기 2단계, 선택 카드 3장, 재굴림 1종과 주사위 교체 1종, 장비 슬롯별 소수 샘플은 프로토타입 제안이다. 카드 풀 최대 장수와 최종 콘텐츠 수를 이 표로 확정하지 않는다.

## 13.2 구현 진행안

**첫 단계 — 기반 검증:** Unity 6.6 Android 빈 빌드와 Firebase 인증·App Check 최소 연동을 확인한다. 동시에 데이터·난수·패 판정 규칙을 UI 없이 시험할 수 있게 준비한다.

**두 번째 — 전투 루프:** 적 예고, 6주사위, 자동 패 판정, 슬롯별 등급, 빈 고등급 대체 강화, 1장 실행, 승패를 연결한다. 네 장의 행동카드만 사용한다.

**세 번째 — 한 구간 완주:** 노드 선택부터 5종 사건, 혼합 성장, 대운명, 결과 화면, 저장·복귀까지 연결한다. 주사위 성장과 태그 장비의 효과를 한 번 이상 경험하도록 구성한다.

**네 번째 — 제한 검증 결합:** 서버 런 시작·체크포인트·정산, 영구 소유권 검증, 중복 처리·권한·비용 테스트를 연결한다. 공개 보상에 반영하기 전에 검증 경계를 확인한다.

## 13.3 통과 기준

정상 런을 시작부터 대운명까지 마칠 수 있고, 생성된 모든 행동카드가 사용 가능해야 한다. 사건당 진척은 한 번만 증가하며, 선택하지 않은 길로 돌아갈 수 없어야 한다. 재시작이 무료 재굴림·보상 복제로 이어지지 않아야 한다.

재미 검증에서는 주사위 반복 피로, 카드 선택의 의미, 노드 경로의 가치, 주사위 투자와 직접 전투력 투자의 균형을 본다. 전투·탐험의 등급 분포와 주사위 성장 전후를 각각 기록한다. 보안 연결 완료와 재미 검증 완료는 서로 다른 결과로 관리한다.

# 14. 결정 대기와 범위 관리

## 14.1 해당 기능 구현 전에 정할 것

| 항목 | 결정할 내용 | 지금의 처리 |
|---|---|---|
| 패·확률 | 임시 서열·가중치, 운명력 범위·동률 | 버전 있는 시험 데이터 사용 |
| 전투 수식 | 피해·보호량·만료·반올림 | 최소 공통 수식만 확정 |
| 운명 상한 | 설정 시점, 재분배, 보너스, 대운명 예외 | 제안과 확정 규칙을 분리 |
| 비어 있는 풀 | 등급별 사건 부족·전체 행동 풀 소실 | 데이터 검사; 초기 삭제 미구현 |
| 임시 강화 | 원등급보다 낮은 슬롯으로 대체되는 경우 | 삭제·고등급 와일드 확장 전 결정 |
| 조작 자원 | 재굴림 횟수·탐험/전투 공유·회복 | 시험 효과 1종만 수치화 |
| 보상·레벨 | 경험치 출처·레벨 표·HP 증가 처리 | 임시 성장표 사용 |
| 보안 | 체크포인트·전투 검증 깊이·오프라인 | 영구 보상 공개 전 결정 |

이는 큰 게임 방향을 다시 설계하라는 의미가 아니라 구현 시 빈칸으로 둘 수 없는 경계 규칙이다. 해당 모듈 착수 시 최소값을 정하고 테스트 결과로 조정한다.

## 14.2 이후로 미루는 것

신규 캐릭터·복잡한 스택, 다중 적·파티, 상세 상태이상, 많은 행동카드, 스킬 삭제·교체 UI, 추가 장비 슬롯, 장비 제작·강화·대형 인벤토리, 광범위한 태그 연쇄, 특수 던전, 무한 모드, 최종 점수 산식, 경제·과금 체계는 초기 루프의 필수 요소가 아니다.

기능을 미룬다는 것은 영구히 금지한다는 뜻이 아니다. 데이터와 책임 경계는 열어두되, 아직 쓰지 않는 범용 기능을 선행 구현하지 않는다.

## 14.3 이전 답변에서 보완한 내용

‘구현을 막는 문제가 전혀 없다’고 단정하기보다, **핵심 루프 구현은 시작할 수 있고 경계 규칙·실기기·보안 검증은 남아 있다**고 표현하는 것이 정확하다.

또한 고등급 = 자동 진척 가속, 운명카드 3장 공통 등급, 와일드 카드 우대, 공통 행동력, 상시 기본 공격은 현행안이 아니다. 태그·장비 수치와 보안 구성의 상세 제안도 사용자에게 이미 확정받은 게임 규칙처럼 취급하지 않는다.

**현재 결론:** 콘텐츠를 더 늘리기보다 최소 전투와 한 구간 완주를 구현한다. Google 로그인만으로 치트 방지가 끝난다고 보지 않고, Firebase 기반의 인증·앱 검증·권한·제한적 게임 검증·보상 정산을 분리해 설계한다.
