## 문서 사용 기준

현재 관찰, 유지할 게임 규칙, 구조 적용안, 후속 기능을 구분한다. 문서에 등장하는 클래스·인터페이스 이름은 적용 시 책임을 설명하기 위한 권장 명칭이며, 모두 이미 구현되어 있다는 뜻이 아니다. 실제 작업을 시작할 때 기준 커밋 이후 변경과 작업 대상 파일을 확인한다.

**진행 요약:** A 시드·연출 → B 상태·저장 경계 → C 순수 코어·정의 분리 → D 신규 카드·등급별 상점 → E 계정·서버 연결.

**읽기 순서:** 1–4장 목표·개선 범위 / 5–10장 책임·데이터·패턴 / 11–13장 저장·적용·검증 / 14–15장 비목표·근거.

## 1. 목표와 선택한 접근

현재 한 구간 플레이 루프를 보존하면서 신규 캐릭터·행동카드·장비·사건을 추가하기 쉬운 구조를 만든다. SOLID를 명분으로 모든 클래스를 인터페이스화하거나 다른 게임에도 쓰일 범용 엔진을 선행 제작하지 않는다.

검토 가능한 접근은 다음과 같다.

| 접근 | 장점 | 부담 | 판단 |
|---|---|---|---|
| 현재 구조에 콘텐츠·조건 분기만 추가 | 단기 작업이 작다 | 캐릭터·효과 증가 시 RunSession과 UI의 변경 범위가 커질 수 있다 | 단기 유지에는 가능 |
| 기능별 모듈 + 순수 C# 코어 + Unity·저장 어댑터 | 기존 규칙을 살리면서 변경 경계·테스트 경계를 명확히 한다 | 데이터·직렬화 경계를 단계적으로 옮겨야 한다 | 권장 |
| 범용 ECS·전면 이벤트 소싱·대형 플러그인 프레임워크 | 광범위한 확장 목표에 대응할 수 있다 | 현재 필요보다 많은 기반 작업과 마이그레이션 부담 | 현 단계 제외 |

권장 조합은 **데이터 기반 콘텐츠 + 단일 런 상태 변경 경로 + 조합형 효과 + 표시/저장 어댑터**다. 패턴 이름의 개수가 아니라 신규 콘텐츠를 추가할 때 변경해야 하는 범위를 줄이는 것을 성공 기준으로 삼는다.

## 2. 유지할 게임 규칙

Android·세로 고정·모험가 1명 대 적 1개체, 6주사위·최고 패 자동 판정, 카드별 등급 추첨을 유지한다. 패 판정 우선순위와 운명력은 분리한다. 탐험·전투 확률표도 분리한다.

노드 유형과 같은 카드 최소 1장, 나머지 유형 편향, 카드 중복 허용을 유지한다. 선택 전 운명카드는 유형·등급만 공개한다. 일반 사건 해결은 정확히 한 번 진척 +1이다. 2026-09-10 승인된 신규 생성 모드1은 설정된 일반층 뒤 미리 생성한 단일보스로 합류하며, 기본은 일반10층+보스1층이다. 임계점에서 일반 노드를 일괄 대운명화하지 않는다. 기존 저장의 모드0만 원래의 임계점 이후 선택 노드 전환 규칙을 유지한다. 변경 계약은 [PROCEDURAL_CAMPAIGN_PLAN](Plans/PROCEDURAL_CAMPAIGN_PLAN.md)을 따른다.

전투의 제시 카드는 공통 MP·행동력·쿨다운 없이 사용할 수 있어야 한다. 역할 보장 슬롯과 상시 기본 공격은 추가하지 않는다. 조건부 효과는 사용권을 잠그지 않는 방향을 유지한다. 와일드 카드의 추첨 우대도 넣지 않는다.

HP·위력·수호와 무기·방어구·장신구를 유지한다. 수호는 방어 행동의 보호량에 사용하며 상시 피해 감소로 바꾸지 않는다. 레벨업과 운명 보상의 혼합 성장을 유지한다.

현재 구현 계획에서 채택한 재굴림은 주사위 1개와 카드 후보 재생성을 포함한다. 이를 ‘카드 공개 전만 재굴림’으로 바꾸는 것은 구조 정리가 아니라 별도 게임 규칙 변경이다. 운명 상한의 적용 시점·보너스 방향도 이번 구조 작업에서 임의 변경하지 않는다. [C1, C2]

### 3.3 적용 순서

**A → B → C → D** 순서로 진행하고, 계정·서버 연결은 후속 **E**로 분리한다. IMP-04의 확률·성장 체감 비교는 A의 플레이 준비와 D의 콘텐츠 시험에서 확인한다. IMP-08의 Android 검증은 한 번으로 끝내지 않고 실제 변경이 반영된 빌드에서 수행한다. 단계별 범위는 12장을 따른다.


IMP-03은 심층 콘텐츠 제작이 아니다. 먼저 표시 가격·구매 가격·재개 가격을 같은 결정 결과로 연결한다. 훈련 보상을 모든 휴식 등급에서 같게 둘지는 별도 정책으로 명시한다. 구조 변경 중 밸런스까지 동시에 바꾸지 않는다. 현재 관찰의 근거는 기준 커밋의 설정·세션·화면 코드다. [C2–C6]

## 4. 현재 코드에서 살릴 것과 분리할 것

### 4.1 유지할 기반

DiceRules의 명시적 난수 상태, 패 우선순위와 운명력 분리, FateCardRules의 슬롯별 추첨과 유형 보장, CombatRules의 플레이어 행동→사망 확인→생존 적 반응, GrowthRules의 태그 조건 수치 보정은 보존 대상이다.

RunSession의 복제 상태 계산→체크포인트 저장→성공 후 현재 상태 교체 흐름도 유지한다. 처리한 보상 ID와 해결한 사건 ID를 분리한 의미를 변경하지 않는다. [C2, C7–C9] UIManager·BaseUI·SceneFlow와 현재 프리팹을 새 UI 프레임워크로 교체하지 않는다.

### 4.2 단계적으로 분리할 책임

| 현재 요소 | 권장 변경 | 지금 하지 않을 일 |
|---|---|---|
| FateDiceConfig / GameConfigData | 게임 정의와 PresentationSettings, SO 편집용 코드와 순수 데이터 분리 | 모든 콘텐츠를 즉시 개별 SO 수백 개로 변환 |
| RunSession | 상태 변경 진입점 유지, 명령별 게임 처리와 저장 조율 책임 구분 | 모든 메서드를 파일/서비스 하나씩으로 분할 |
| RunState | 룰 실행 전용 가변 상태와 외부 표시 스냅샷 분리 | 읽기 전용 인터페이스만 씌우고 내부 가변 객체 그대로 노출 |
| RunUIController | 입력·화면 전환·연출 유지, DTO 매핑과 저장 조율을 단계적으로 추출 | UI 프리팹·씬·기존 연결을 전면 재생성 |
| LocalRunStore | 파일 읽기·쓰기·체크섬·포맷 처리 담당, 게임 상태 검증은 순수 검증기로 분리 | 체크섬을 치트 방지 증명으로 사용 |
| CombatRules / GrowthRules | 동일 효과 계산 함수를 표시와 실행에서 공유, 효과 확장점만 추출 | 동작이 없는 빈 효과 타입·전역 매니저 양산 |

## 5. 네 가지 책임 경계

### 5.1 게임 규칙: Domain

순수 C#으로 주사위, 패, 확률, 전투, 성장, 노드, 효과, 상태 유효성을 다룬다. 파일·네트워크·Unity 생명주기·화면 시간을 참조하지 않는다. 임의 전역 Random이나 현재 시각을 읽지 않는다.

외부에서 난수 상태와 명령을 전달받아 계산한다. 지금의 stateless static 계산 함수는 그대로 사용할 수 있다. SOLID 준수가 모든 static 함수의 제거를 뜻하지 않는다.

### 5.2 진행 조율: Application

새 런·이어하기·노드 선택·굴림·카드 선택·보상 수령의 요청을 받아 처리 순서와 저장 경계를 관리한다. 로컬 저장 인터페이스와 결과를 표시할 읽기 모델을 연결한다.

RunSession은 기존 공개 진입점을 유지하는 facade가 될 수 있다. 당장 완전히 새로운 서비스를 병렬로 만들 필요는 없다. 커질 때 전투·사건·보상 단위로 내부 처리기를 분리한다.

### 5.3 화면: Presentation

기존 uGUI 화면, 입력, 카드·주사위 애니메이션, 번역, 화면 전환을 담당한다. 읽기 전용 표시 스냅샷과 확정된 결과를 받아 그린다. 화면이 보상을 지급하거나 애니메이션 종료가 적의 피해를 계산하지 않는다.

화면에서 플레이 시간을 측정할 수는 있다. 단, 읽기 전용 RunState의 필드를 직접 수정하지 않고 진행 조율 계층의 시간 기록 경로에 전달한다. 매 프레임 파일을 저장하지 않는다.

### 5.4 외부 기술: Infrastructure

LocalRunStore, 저장 포맷/마이그레이션, 시드 공급, 향후 Firebase 인증·서버 검증 통신을 담당한다. 코어가 정한 작은 인터페이스를 구현하며, 코어가 Firebase SDK를 참조하지 않는다.

의존성은 다음처럼 향한다. 이는 컴파일 의존 관계이며 게임의 시간적 실행 순서와는 다르다.

- Presentation → Application → Domain
- Infrastructure → Application의 경계 인터페이스 및 Domain의 필요한 데이터
- Composition Root → 위 요소를 생성·연결
- Domain → Presentation/Infrastructure/Unity 의존 금지

초기에는 Domain과 Application을 하나의 FateDice.Core 어셈블리에 넣어도 된다. 논리적 책임 분리가 모든 계층의 별도 패키지화를 요구하지는 않는다.

| 콘텐츠 정의 | 캐릭터 초기 능력, 카드 기본 등급·효과·태그, 장비, 적, 사건·상점 풀 | 제작 도구에서 편집 |

| 런 상태 | 현재 HP, 레벨, 장비, 소유 행동, RNG, 확정 카드, 진행·보상 기록 | 승인된 로컬 게임 명령 |
| 계정 영구 상태 | 카드 소유권, 해금, 서버 승인 재화 | 출시 단계에서 서버 권위 |
| 표시 설정·표시 DTO | 아이콘, Sprite, 색상, 연출 속도, 공개 가능한 정보 | UI 계층 |

SO는 제작용 원본이다. SO 원본을 런마다 직접 변경해 HP·강화치·소유 정보를 저장하지 않는다. 런의 카드 강화도 원본 카드 정의가 아니라 런별 상태로 저장한다. Unity 빌드의 영구 저장은 별도 직렬화/파일 또는 서버 저장을 사용한다. [R3]

현재 하나의 설정 자산을 유지하면서 내부 데이터부터 분리할 수 있다. 이후 실제 편집 부담이 커지는 순서대로 캐릭터·행동·장비 카탈로그 자산을 나눈다. 새 런의 규칙은 기본적으로 고정하고, 배포된 밸런스 변경을 진행 중 런에 무단 적용하지 않는다.

ID의 의미도 구분한다. contentId는 화염구라는 정의, offeredCardId는 이번 추첨의 특정 슬롯, nodeId는 이번 런의 특정 사건 위치다. 같은 contentId가 여러 번 나와도 서로 다른 offeredCardId를 유지한다. 소유 카드 중복 정책은 현재의 ID 집합 의미를 보존하고, 동일 카드 여러 장 보유는 별도 기획 변경으로 다룬다.

## 7. 적용할 패턴과 적용하지 않을 범위

### 7.1 Command — 입력을 게임 명령으로 표현

RollDice, RerollDie(index), ChooseNode(nodeId), ChooseFate(offeredCardId), ChooseAction(offeredCardId), ClaimReward(rewardId), BuyProduct(productId)를 명시적 요청으로 만든다.

화면 클릭이 피해량·골드 증가량을 지정하지 않고 선택한 안정 ID를 전달한다. 명령은 실행 취소 기능을 의미하지 않는다. 운명 선택을 되돌리는 Undo는 제공하지 않는다.

가벼운 불변 요청 DTO와 처리 함수로 시작한다. 처음부터 반사 기반 명령 버스·전역 라우터·모든 명령용 별도 서비스가 필요하지 않다. 현재 bool API를 호환 facade로 유지하고, 내부에서 수락 여부·오류 코드·다음 표시 상태를 반환하도록 전환할 수 있다.

명령 경계 계약:

1. 현재 runId·phase·sequence와 선택 ID·자원을 검사한다.
2. 이전 상태에서 독립된 후보 상태를 만든다. 불변 규칙 카탈로그는 공유할 수 있으나 가변 목록은 공유하지 않는다.
3. 규칙을 실행하고 후보의 RNG·카드·비용·보상 처리 ID를 함께 갱신한다.
4. 상태 유효성을 검사하고 단일 런 체크포인트로 저장한다.
5. 저장 성공 후 런 상태를 교체하고 확정 결과/연출 정보를 공개한다.
6. 저장 실패는 이전 상태 유지다. 저장 성공 뒤 UI 오류는 게임 명령 재실행이 아니라 확정 상태 재표시로 복구한다.

명령을 동시에 처리하지 않는다. 저장이 비동기화되더라도 단일 실행 경계를 유지하며, 오래된 UI 요청은 sequence 또는 확정 후보 ID로 거부한다.

### 7.2 명시적 상태 머신 — 진행 단계와 연출 단계 분리

현재 RunPhase를 보존하고 허용 명령·전이 규칙을 한곳에서 검사한다. 단순한 enum과 전이 검증으로 시작한다. 모든 phase마다 IState 클래스를 만들 필요는 없다.

CombatCards에서만 ChooseAction이 허용되는 것은 카드 사용 비용 제한과 다르다. 합법적으로 제시된 카드의 사용은 여전히 보장하되, 이전 턴 카드나 두 번 처리된 입력은 거절한다.

입력 잠금, 주사위 굴림 연출, 피해 연출은 게임 phase와 다른 UI 상태다. 연출 중 앱이 종료되어도 확정 결과를 복원하며 피해를 다시 실행하지 않는다.

### 7.3 Strategy + Composition — 카드는 효과를 조합한다

카드마다 FireballCard, IceballCard 같은 상속 클래스를 만들지 않는다. 숫자·태그·효과 구성이 다른 카드는 같은 데이터 형식을 사용한다.

예시:

- 화염구: [불][마법][투사체][공격] + 적에게 Damage(위력 계수 2.3)
- 얼음 투사체: [얼음][마법][투사체][공격] + 적에게 Damage(다른 위력 계수)
- 방어: [방어] + 자신에게 Block(수호 계수 1.5)
- 불꽃 방패: [불][마법][방어] + 자신에게 Block(수호 계수)

이는 구조 설명용 후보이며 새 카드를 지금 전부 추가한다는 뜻은 아니다. 초기 처리기는 Damage·Block 두 종류만 사용한다. 새로운 효과가 필요한 시점에 해당 처리기·검증·표시·테스트를 같이 추가한다.

EffectResolver는 정의된 효과 목록을 안정적인 순서로 실행한다. 처리기 등록은 앱 조립 지점에서 명시한다. 미지원 효과는 콘텐츠 검증에서 거부하고, 플레이 도중 사용 불가 카드로 생성하지 않는다. 모든 효과가 같은 명령 후보 상태만 변경하게 한다.

순수 수치 효과는 미리보기와 실행이 같은 계산 경로를 사용한다. 미리보기는 RNG·상태를 소비하지 않는다. 태그 배율·등급 비율·반올림·보호막 만료 순서는 기존 규칙을 보존한다.

### 7.4 태그 조건 + Modifier — 대상과 바꾸는 값을 명시

기존 Any/All/None 및 카드/장착 장비 태그의 구분을 유지한다. 조건 검색 대상과 수정 대상은 반드시 별개로 명시한다.

예: 조건 대상=현재 카드, 조건=불 태그, 수정 대상=피해, 연산=가산 비율 +25%.

태그가 붙었다고 화상이나 추가타를 자동으로 실행하지 않는다. 태그 판정·수치 보정·실제 효과 실행을 분리한다. 장비 변경 시 누적 배율을 영구 수정하기보다 현재 장착 상태로부터 파생값을 계산하여 중복 적용을 피한다.

새 트리거·상태 효과를 도입할 때 처리 순서를 정의한다. 전역 이벤트 버스의 구독 순서로 전투 결과를 결정하지 않는다. 추가 행동 연쇄는 도입 시 종료·재귀 규칙을 갖추며, 이번 작업에서 범용 트리거 언어를 만들지 않는다.

### 7.5 Presenter·Adapter·Composition Root

기존 RunUIController를 유지하면서 RunViewModelBuilder 같은 순수 매핑 책임을 먼저 추출한다. 필요해질 때 탐험·전투 단위 Presenter를 나눈다. UIManager와 기존 프리팹을 교체하지 않는다.

초기 외부 경계는 ISeedSource와 IRunStore 정도부터 시작한다. 시드는 일반 공급자와 고정 테스트 공급자를, 저장은 파일 저장과 실패 주입용 테스트 저장을 같은 계약으로 시험한다.

IRunStore는 로컬 런 체크포인트 계약이다. 서버 검증·영구 재화 정산을 동일한 Save 함수의 구현 교체로 위장하지 않는다. 서버 기능이 실제로 도입될 때 별도의 계정 조회·런 제출 인터페이스를 만든다.

GameApplication을 조립 지점으로 사용해 의존성을 생성자·초기화 인자로 주입한다. 신규 DI 패키지 설치나 전역 서비스 로케이터가 선행 조건은 아니다. 확정 결과의 알림은 연출·분석용으로만 사용하며, 보상 지급을 UI 구독자에 맡기지 않는다.

개방-폐쇄가 코드 변경 금지를 뜻하지 않는다. 새로운 개념은 처리기·등록·검증·테스트를 추가할 수 있다. 다만 관련 없는 기존 카드·세션 분기를 반복해서 수정하지 않도록 한다. SOLID 일반 원칙은 Microsoft 자료, Unity의 패턴 적용 지침을 참고했다. [R1, R2, R5]

새 캐릭터 스택이나 상태이상은 초기 범위를 자동으로 확장하지 않는다. 향후 고유 규칙이 필요할 때 상태의 수명(전투/구간/런), 만료, 저장, 재연 순서를 정의한다.

## 10. 어셈블리와 폴더 적용

현재 Features 아래의 기능 중심 폴더를 유지한다. 파일 정리만을 위해 모든 경로·namespace를 일괄 변경하지 않는다.

초기 목표 어셈블리는 다음으로 충분하다. 아래 이름과 경계는 구조 적용안이며, 현재 이미 분리가 완료되었다는 의미는 아니다.

- **FateDice.Core:** 게임 규칙·런 상태·진행 계약. No Engine References 사용을 목표로 한다.
- **FateDice.Runtime:** 기존 이름 유지. SO 편집 데이터의 변환, Unity 화면·연출·조립, 로컬 저장 어댑터를 점진 배치한다.
- **기존 FateDice.SharedUI / Editor / Tests:** 유지하고 변경된 참조만 조정한다.

Domain과 Application은 처음에는 같은 Core에 논리적으로 분리한다. Firebase 전용 어셈블리는 SDK를 실제 연결할 때 추가한다.

현재 Runtime 루트에는 uGUI·InputSystem·SharedUI 참조가 있다. Core를 만들 때 하위 Domain 폴더를 새 코어 asmdef 또는 그 asmref로 묶고, 기존 UI 스크립트의 어셈블리를 그대로 유지한다. [C10] 새 Core가 Runtime을 참조하는 순환 의존을 만들지 않는다. Unity Assembly Definition/Reference로 폴더 위치와 컴파일 경계를 연결할 수 있다. [R4]

MonoBehaviour·ScriptableObject 이동은 GUID와 직렬화 타입 연결에 영향을 주는 작업으로 따로 검증한다. 기존 .meta 보존, Editor 도구를 이용한 제한된 자산 변경, Missing Script·참조 검사 없이 대규모 이동을 하지 않는다.

## 11. 저장과 서버를 위한 최소 계약

### 11.1 로컬 저장

저장 schemaVersion, 게임 rulesVersion, contentVersion은 의미를 구분한다. 현재 한 문자열을 즉시 복잡한 버전 관리 시스템으로 바꾸기보다, 저장 구조가 달라지는 실제 작업에서 새 버전과 대응 방식을 명시한다.

Core의 후보 상태 복제는 Unity JSON에 의존하지 않는 명시적 복제를 목표로 한다. 규칙 카탈로그는 런 시작에 불변화하고, 변경되는 상태만 복제할 수 있다. 디스크에는 런 규칙 스냅샷을 계속 보존하여 기존 런이 최신 자산에 영향받지 않도록 한다. 단순히 contentId만 저장하고 현재 SO를 읽는 방식으로 되돌리지 않는다.

구형 저장은 조용히 초기화하지 않는다. schema1 읽기 전용 DTO/어댑터를 유지하거나 검증된 마이그레이션을 적용한다. 지원하지 않는 형식은 명확히 알리고 원본을 보존한다. 데이터 스냅샷만 보관해도 예전 코드 규칙이 자동 보존되는 것은 아니므로, 실제 수식 변경 시 rulesVersion의 지원 범위를 정한다.

### 11.2 기록과 향후 검증

명령 기록을 도입할 때 runId, sequence, commandKind, 선택한 ID, 필요한 인자와 rules/content 버전을 기록한다. UI 연출 시간은 게임 규칙 재연의 입력으로 사용하지 않는다. 플레이어가 선택한 ID와 명령 인자는 재연에 포함하되, 클라이언트가 보고한 결과값을 검증 없이 정답으로 받아들이지 않는다. 기존 단일 RNG 알고리즘과 소비 순서를 구조 변경에서 유지한다. 다중 난수 스트림 전환은 별도 규칙 버전 작업이다.

순수 C# 코어 분리만으로 Firebase 측에서 같은 코드를 실행할 수 있다는 뜻은 아니다. 서버가 다른 언어·런타임을 사용하면 선택한 검증 규칙의 대응 구현과 공통 난수·반올림·효과 순서 테스트 벡터가 필요하다.

명령 로그를 갖추는 것과 치트 방지는 다르다. 클라이언트가 기록 전체를 위조할 수 있으므로 서버 시작 상태·규칙·승인 기록과 필요한 재연이 따로 필요하다. 초기에는 스냅샷 복귀를 유지하고, 선택적 명령 로그를 추가하더라도 전면 이벤트 소싱으로 바꾸지 않는다.

### 11.3 서버 권위

로컬 체크포인트 성공은 서버 보상 승인과 다르다. Firebase 연결은 로컬 파일 저장의 단순 대체물이 아니라 별도의 권한·제출·정산 기능이다.

보상 중복 의미는 요청 ID 하나가 아니라 서버가 인정한 runId + 사건 인스턴스 + 보상 슬롯으로 판단한다. 영구 계정 보상은 인증·소유권·진행·중복을 서버에서 검증한 뒤 지급한다. Google 로그인과 App Check의 도입만으로 전투 정당성까지 검증되었다고 표현하지 않는다.

## 12. 순차 적용 묶음과 종료 조건

각 묶음은 기존 게임을 실행 가능한 상태로 마친다. 하나의 무제한 ‘SOLID 리팩터링’ 목표로 합치지 않는다.

### A. 반복 플레이 검증 준비

대상: RunUIController/새 런 시작, 작업실 고정 시드 연결, PresentationSettings/DiceRollUI 시간.

일반 시드 공급과 고정 주입을 분리하고 탐험·전투 연출 시간을 조정 가능하게 한다. 같은 시작 스냅샷·명령열의 게임 결과가 전후 동일해야 한다. 서로 다른 새 런을 비교한다면 runId·경과시간처럼 별도 생성되는 메타데이터는 분리하고 패·콘텐츠 ID·등급·스탯·RNG를 비교한다. 새 시드 테스트는 ‘두 번 결과가 우연히 절대로 같지 않다’가 아니라 공급자 호출과 고정 입력 재현 계약으로 검사한다.

최신 Android 시험 빌드에서 정상 터치와 중단 복귀를 먼저 확인한다. 실기기가 없으면 해당 검증만 미실행으로 남긴다.

### B. 런 상태 변경·저장 경계 분리

대상: RunSession, RunState, LocalRunStore, RunUIController의 새 런/이어하기/시간 기록, 관련 저장·전투 테스트.

IRunStore 경계와 읽기 전용 표시 스냅샷을 도입한다. 상태 복제→저장→공개 순서, 실패 시 무변경, 보상과 진척의 단일 처리를 보존한다. 기존 공개 API의 facade로 UI를 단계적으로 연결한다. 시간 값은 게임 명령 RNG를 소비하지 않는다.

### C. 순수 규칙 코어와 정의 데이터 분리

대상: FateDiceConfig/GameConfigData, Dice/Fate/Combat/Growth 규칙, asmdef/asmref, 코드 이동에 직접 영향받는 요약·테스트.

게임 정의에서 Unity 표시 타입·에디터 속성·SO 의존을 추출한다. Core의 Unity 참조를 차단하고 기존 규칙 열거·명령 시나리오를 통과시킨다. 불변 카탈로그 공유는 원본 SO나 외부 가변 DTO의 공유와 다르다는 점을 검사한다. 저장 포맷 변경이 있으면 같은 묶음에서 구형 저장 대응을 검증한다.

### D. 콘텐츠 확장점을 실제 기능으로 검증

대상: 캐릭터 정의, 행동 효과 정의/처리기, 보상 정의/처리, 등급별 상점 정책과 표시.

Damage·Block 효과 조합을 먼저 도입하고 기존 카드의 결과를 보존한다. 새 Damage 카드 한 장을 데이터로 추가하고 런 중 AddAction 보상으로 획득하게 한다. 화면·세션에 카드 ID 분기를 추가하지 않고 추첨·사용·재개가 가능해야 한다.

상점은 등급별 수치 정책 한 종류를 적용하고, 입장 시 확정한 상품/가격이 표시·차감·저장·이어하기에서 같음을 검사한다. 구매 또는 화면 재개로 상품이 무료 재생성되지 않는다.

### E. 계정·서버 기능 연결 — 후속 작업

로컬 플레이가 안정된 뒤 Google/Firebase 인증과 제한 검증·영구 소유권·정산을 별도 범위로 연결한다. 최초 SDK·Android 호환 시험은 더 일찍 수행할 수 있으나, 운영 정산의 완료 조건을 로컬 프로토타입 통과 조건과 섞지 않는다.

## 13. 핵심 회귀 검사

- 동일 시작 스냅샷·명령열의 패/카드/최종 규칙 상태 동일, UI 표시만 바꿔도 RNG 불변. 새 런 간 비교에서는 runId·경과시간을 별도 취급한다.
- 현재 10패의 전체 46,656 결과 검사와 기존 우선순위 유지.
- 카드마다 등급 추첨, 유형 최소 1장 보장, 중복 허용, 와일드 우대 없음.
- 고등급 빈 풀 대체가 원본 카드 정의를 변경하지 않음.
- 비용·쿨다운에 의한 제시 카드 비활성화 없음. 이전 턴 ID는 거절.
- 저장 실패 시 HP/비용/난수/후보/처리 ID 모두 이전 상태 유지.
- 저장 성공 후 UI 복구가 명령·보상을 재실행하지 않음.
- 상점 구매는 추가 진척 없음, 사건 종료는 정확히 한 번 +1.
- 태그 조건·피해·보호량·반올림·보호막 만료·처치 후 반격 억제 보존.
- 구형 저장·지원 불가 저장은 원본 보존, 무료 재굴림·보상 복제 없음.
- 신규 카드 획득이 현재 런에만 반영되고 새 런/원본 정의를 오염시키지 않음.
- 최신 Android: 실제 카드 터치, 비율·Safe Area, 굴림/카드/보상 단계에서 중단·재개.

보고서에 적힌 기존 테스트 통과 수를 이 구조 변경의 PASS로 재사용하지 않는다. 변경된 코드에서 필요한 테스트를 실제 실행하고 확인한다. 일반 개선 제안은 후속 목록으로 두고, 각 묶음의 필수 조건을 충족하면 종료한다.

## 14. 이번 설계에서 제외한 것

범용 스킬 그래프 에디터, 모든 게임에 재사용할 전투 패키지, 광범위한 상태이상·트리거 언어, 마이크로서비스, ECS 전환, 전면 이벤트 소싱, 카드별 거대 상속 트리, 전역 이벤트 버스 중심 게임 계산, 신규 DI 라이브러리 강제, Addressables 전환, UI Toolkit 전면 재작성은 이번 권장 범위가 아니다.

최종 목표는 **기존 한 구간을 유지한 채 새 카드·장비·캐릭터 정의를 넣어도 저장·UI·전투가 함께 깨지지 않는 것**이다.
