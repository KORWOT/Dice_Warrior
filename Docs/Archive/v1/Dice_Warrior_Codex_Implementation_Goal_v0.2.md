## 1. 목표와 승인 범위

기존 한 구간 플레이 루프를 보존하면서 v0.2의 A→B→C→D를 순차 구현하라.
이 요청은 해당 범위의 계획 작성·코드 수정·직접 관련 자산 연결·검증까지 승인한 구현 요청이다.
계획이나 검토 문서만 작성하고 종료하지 말고, 계획을 기록한 뒤 실제 구현으로 진행하라.
승인된 범위에서 각 단계의 필수 검증을 통과하면 별도 승인 질문 없이 다음 단계로 진행하라.

구현 목표는 다음 네 가지다.
- 일반 새 여정과 고정 시드 테스트를 분리하고 탐험·전투의 연출 속도를 조정 가능하게 한다.
- 런 상태 변경·저장·화면 공개 경계를 명확히 하고 UI의 직접 상태 변경을 제거한다.
- Unity/UI/파일/Firebase 기술에 의존하지 않는 순수 C# 코어를 분리한다.
- 기존 효과를 조합한 신규 행동카드 1종의 런 중 획득과 등급별 상점을 통해 확장성을 검증한다.

문서의 E 단계인 Firebase·Google 로그인·영구 계정 경제·서버 정산은 이번 구현 범위에서 제외한다.
서버 기능을 흉내 낸 구현이나 빈 인터페이스 묶음을 선행 제작하지 않는다.

### 1.1 기존 AGENTS.md를 유지하는 이번 작업의 명시적 승인

AGENTS.md 및 기존 범위별 지침 파일은 수정하지 않는다.
AGENTS 보완 파일을 적용하거나, 같은 목적의 AGENTS.override.md·하위 지침을 새로 만들어
이번 Goal을 우회 적용하지 않는다.

이번 사용자 요청은 다음 사항을 이 작업에 한해 구체적인 지침으로 승인한다.
- v0.2의 A~D에 필요한 코어·상태·저장 경계 분리는 승인된 리팩터링이다.
  기존의 무관한 선행 추상화 금지를 이유로 이 작업 자체를 거부하지 않는다.
- 보조 운영 문서가 없을 때는 2절에 따라 처리하고, 누락 문서 양산을 선행하지 않는다.
- RA-A~D는 구현 전에 고정한 작업 단위이며 7절의 검토·수정 예산을 적용한다.
- 필수 Unity 검증과 Android 환경 부재는 6절의 상태 구분을 적용한다.

이 구체적 승인과 기존 지침의 일반적인 기본값이 충돌하는 경우에만 위 조건을 적용한다.
이를 AGENTS 전체 무시, 검증 면제, 도구 권한 우회 또는 사용자 데이터 변경 허가로 해석하지 않는다.
GDD는 게임 규칙, 설계 v0.2는 구조 방향, 본 Goal은 이번 실행 범위·순서·예외·종료 기준이다.
보호할 게임 규칙의 실질적 충돌은 임의 해석하지 말고 해당 부분만 보고한다.

샌드박스·도구 권한과 실제 접근 제한은 우회하지 않는다.

## 3. 범위와 변경 허용 경계

기존 기능 폴더와 UIManager·BaseUI·SceneFlow·프리팹을 유지하라.
범용 엔진 재작성보다 기존 RunSession 진입점을 살리는 점진적 변경을 우선한다.

허용 범위:
- Assets/_Project의 이번 기능에 직접 관련된 C#·테스트·asmdef/asmref 및 필요한 .meta.
- A~D 적용에 꼭 필요한 설정 자산·Scene·Prefab의 제한적 변경.
- 현재 작업 PLAN/REPORT와 변경 코드의 대응 CodeMap·직접 영향받는 색인.
- 테스트 전용 픽스처와 재현 가능한 확률/동작 검증 도구.

각 단계의 정확한 대상 파일·신규 파일·이동 전후 경로·공통 계약을 수정 전에 PLAN에 적어라.
이 등록은 위 승인 범위 안의 구체화이며 무제한 파일 변경 허가가 아니다.
사용자 변경과 대상이 겹치면 임의 덮어쓰기 없이 해당 충돌을 보고하고, 독립적인 안전 작업만 진행한다.
자산은 파일별로 목적을 적고 승인 범위 안에서 Editor API 또는 기존 승인 도구로 변경한다.
GUID/.meta와 직렬화 연결을 보존하고 기존 Scene/Prefab 전체를 재생성하지 않는다.

금지:
- 사용자 변경의 임의 덮어쓰기, reset, stash, clean, 강제 복구.
- AGENTS.md·기존 범위별 지침·GDD·v0.2 설계 원문의 임의 수정 또는 완료 기준 완화.
- 이전 Goal v0.1·AGENTS Addendum의 병행 적용 또는 새 지침 파일을 이용한 우회.
- 승인 없는 commit·staging·push·merge·브랜치 전환.
- Unity/패키지 업그레이드, 새 DI·ECS·Addressables 패키지 설치.
- 프로젝트 밖 설정, 글로벌 지침·스킬·MCP·hook 변경, 새 계정/클라우드 서비스 생성.
- 폰트·외형 재제작, UI Toolkit 전환, 다중 적/파티, 스킬 삭제 UI, 범용 트리거 엔진.

외부 설치·ProjectSettings 변경 등 위 경계를 넘는 조치가 꼭 필요하면
최소 변경·필요성·영향받는 작업만 보고하고 그 부분만 보류하라.
권한을 얻기 위해 보호 규칙을 수정하지 않는다.

## 4. 보존할 게임 계약

v0.2의 2장과 13장을 기준으로 기존 규칙을 보존하라.
특히 아래는 이번 구조 개선의 임의 변경 대상이 아니다.

- Android·세로 고정·1인 모험가 대 적 1개체.
- 6주사위·현재 10패·최고 패 자동 판정, 우선순위와 운명력의 분리.
- 탐험/전투 확률표 분리, 슬롯별 등급 추첨, 카드 중복 허용.
- 노드 유형 최소 1장 보장과 나머지 유형 편향, 선택 전 유형·등급만 공개.
- 제시 행동카드의 공통 코스트·쿨다운 없음, 상시 기본 공격과 역할 보장 슬롯 없음.
- 와일드 카드 우대 없음, 소유 행동의 ID 집합 의미 유지.
- 빈 등급 대체의 원본 불변, 기존 등급 비율·태그 보정·반올림·보호막 만료 순서.
- 적 처치 후 반격 없음, 일반 사건 진척은 정확히 한 번 +1.
- 현재 재굴림은 주사위 1개와 카드 후보 재생성을 함께 처리한다.
- 운명 상한의 적용 시점·확률 재분배·보상 보너스 방향 유지.
- HP·위력·수호, 장비 3슬롯, 혼합 성장 유지.
- 기존 단일 RNG의 알고리즘·소비 순서 보존. UI와 시간 기록은 규칙 RNG를 소비하지 않는다.

A~C에서는 명시한 시드 공급·표시 변경을 제외하고 게임 결과를 보존한다.
D의 신규 카드·상점 정책은 의도적 콘텐츠 변경으로 별도 기록한다.
특수 주사위를 무조건 상위호환으로 만들려고 확률이나 기존 게임 규칙을 바꾸지 않는다.

## 5. 순차 구현

### RA-A — 시드와 연출 설정

- ISeedSource 또는 동일 책임의 작은 경계로 일반 새 여정과 고정 테스트 시드를 분리한다.
- 일반 새 여정은 새 시드를 요청하고, 작업실/자동 테스트는 고정 시드를 주입할 수 있게 한다.
- 이어하기는 저장된 시드·현재 RNG·확정 카드에서 재개한다.
- 탐험/전투의 굴림 시간과 결과 유지시간을 각각 표시 설정으로 조절한다.
- 현재 연출값을 초기 기본값으로 보존하되, 숨은 최소값 때문에 설정이 무시되지 않게 한다.
- 효과적인 변경 경계까지만 구현하고 다음 단계의 코어 전체를 선행 제작하지 않는다.

완료 조건:
공급자 호출/0 시드 처리/고정 재현/이어하기를 검사하고,
연출값 변경 전후의 규칙 결과와 RNG가 같아야 한다.
랜덤 테스트에 “새 시드나 결과는 두 번 연속 절대로 같지 않아야 함”을 요구하지 않는다.

### RA-B — 런 상태와 저장 경계

- IRunStore는 로컬 체크포인트 계약으로 제한한다.
- RunSession은 상태 변경 진입점으로 유지하고 필요할 때 호환 facade로 연결한다.
- UI에는 분리된 표시 스냅샷을 제공한다. 읽기 전용 목록 안에 원본 가변 객체를 그대로 노출하지 않는다.
- UI의 playedSeconds 직접 수정도 명시적 시간 기록 경로로 옮기되 매 프레임 디스크에 저장하지 않는다.
- 후보 상태 생성→규칙 처리→검증→저장 성공→상태 교체·결과 공개를 유지한다.
- 명령 처리는 직렬화하고, 오래된 카드/노드 ID 및 중복 입력을 거절한다.
- 저장 실패는 이전 상태 유지, 저장 성공 후 UI 오류는 확정 상태 재표시로 복구한다.

완료 조건:
실패 주입 시 HP·비용·RNG·카드·처리 ID가 모두 불변이고,
정상 저장/재개와 중복 입력 거절이 실제 테스트에서 통과해야 한다.

### RA-C — 순수 코어와 정의 데이터

- FateDice.Core를 추가하고 Domain/Application 책임을 논리적으로 분리한다.
- 기존 Runtime·SharedUI·Editor 어셈블리와 기능별 폴더를 최대한 유지한다.
- Core가 UnityEngine·uGUI·InputSystem·Firebase·직접 파일 I/O에 의존하지 않게 한다.
- No Engine References와 참조 구조를 검사하고 Core→Runtime 순환을 금지한다.
- SO 편집 정의, 런 규칙 스냅샷, 가변 런 상태, 표시 설정을 분리한다.
- 후보 상태는 Unity JsonUtility에 의존하지 않는 명시적 복제로 전환한다.
- 불변 카탈로그를 공유할 경우 원본 SO나 외부 가변 DTO와의 별칭 공유를 차단한다.
- LocalRunStore의 게임 상태 검증을 순수 검증기로 분리한다.
- 저장 구조가 달라지면 같은 단계에서 schema1 읽기 또는 검증된 마이그레이션을 제공한다.
- 기존 런의 규칙 스냅샷을 유지한다. 저장된 ID만으로 최신 SO를 다시 읽는 방식으로 바꾸지 않는다.
- 구형 null/빈 DTO와 안정 ID의 의미를 보존하고 지원 불가 저장은 원본을 보관한다.

완료 조건:
Core의 참조 차단·컴파일, 46,656 패 검사, 기존 명령 시나리오의 결과 보존,
스냅샷 독립성과 구형 저장 복원을 통과해야 한다.

### RA-D — 확장성을 실제 콘텐츠로 검증

- 카드별 상속 대신 Damage·Block 효과 정의와 명시적 처리기 조합을 사용한다.
- 기존 카드의 수치·적용 순서·태그·임시 등급 보정을 보존한다.
- 미리보기와 실행은 같은 수치 계산을 사용하며 미리보기가 상태/RNG를 소비하지 않는다.
- 미지원 효과는 제작/시작 검증에서 거절하고, 런 중 사용 불가 카드로 노출하지 않는다.
- 기존 Damage 처리기를 사용하는 신규 행동카드 정확히 1종을 데이터로 추가한다.
- AddAction 보상으로 현재 런에서 획득→행동 풀 반영→추첨→태그 적용→사용→재개를 연결한다.
- 이미 보유한 행동을 다시 얻으면 중복 소유·추첨 우대를 만들지 않는다.
  나머지 보상과 사건 종료는 정상 처리하고 이를 시험 정책으로 기록한다.
- 세션/화면에 신규 카드 ID 분기를 추가하지 않는다.
- 상점은 등급별 가격 배율 한 축만 우선 적용한다.
  품목 추가·리필·상품 수량 체계까지 확장하지 않는다.
- 시험 카드 값과 가격 배율은 PLAN에 먼저 기록하고 데이터로 편집 가능하게 한다.
  수치의 최적성을 이번 구현 완료 조건으로 삼지 않는다.
- 상점 입장 시 확정된 상품/가격을 표시·차감·저장·재개에서 공유한다.
  구매나 재진입을 무료 재생성 기회로 만들지 않는다.
- RA-D에서 AddAction·확정 가격 등 저장 필드를 추가할 때도 같은 단계에서 구형 저장을 검증한다.
  이전 런의 행동 풀·대기 보상·상점 가격에 새 시험 콘텐츠를 소급 주입하지 않는다.
- 휴식 훈련의 공통 보상은 이번에는 유지하고 미변경 정책임을 기록한다.
- 특수 주사위는 기본/1개 교체/여러 개 교체 분포를 별도 비교한다.
  독립 수학 모델과 실제 게임 RNG 표본을 구분하고 성장 방향을 보장한다고 과장하지 않는다.

완료 조건:
신규 카드의 획득·실제 추첨·사용·태그 효과·저장 복원,
새 런/원본 비오염, 상점 표시·차감·재개 일치가 통과해야 한다.
기존 한 구간 완주와 패배·재시작도 유지해야 한다.

## 6. 검증과 환경

실제 설치된 Unity 버전·기존 CLI/Pipeline 등 승인된 실행 채널을 확인하고
현재 사용할 명령·시험 자산·실행 경로를 PLAN에 기록하라.
기존 도구용 스킬은 실제 존재하고 필요한 경우 해당 부분만 읽는다.
동일 프로젝트의 Unity 실행을 직렬화하며 잠금 파일을 지우거나 중복 Editor를 띄우지 않는다.

- 변경 전 관련 회귀의 기준 상태를 확보한다.
- 신규 기능/버그 수정은 실패 사례를 먼저 확인하고, 구조 변경은 기존 동작 보존 테스트를 먼저 확보한다.
- 각 단계에서 변경 영향 테스트와 기존 루프 스모크 테스트를 실행한다.
- D 종료 후 최신 트리의 전체 관련 EditMode/PlayMode와 한 구간 완주를 확인한다.
- 예전 128/128·77/77 기록이나 현재 테스트 개수만으로 PASS를 선언하지 않는다.
- 테스트를 없애거나 assertion을 약화해서 통과시키지 않는다.
  구조 변경으로 테스트 접근 경로를 바꿀 때도 행동 보장과 독립 기대값은 보존한다.
- 같은 시작 스냅샷·명령열의 패·콘텐츠 ID·등급·피해·보상·진척·RNG를 비교한다.
  별개 새 런을 비교할 때 runId·경과시간 등 정규화 항목은 명시하며,
  재연에 필요한 선택 ID·명령 인자를 통째로 제외하지 않는다.
- 자동 시험은 격리된 저장 경로·복사본을 사용한다. 실제 사용자 저장을 덮어쓰지 않는다.
- Android 빌드는 환경이 갖춰졌을 때 최신 코드로 수행한다.
  실기기에서 터치·세로 비율·Safe Area·굴림/카드/보상 단계의 중단·복귀를 확인한다.

Unity/필수 테스트 실행이 불가능하면 해당 단계는 WAIT_VALIDATION이다.
그 증거에 의존하는 다음 단계로 완료 처리하며 넘어가지 않는다.
Android 모듈·기기가 없는 경우에는 Android 항목만 NOT_RUN으로 분리하고,
필수 코드·Editor 검증이 통과한 다음 단계의 로컬 작업은 계속할 수 있다.
실행 가능한 시험의 실패는 “환경 없음”이나 NOT_RUN으로 바꾸지 않는다.

## 7. 계획·검토·중단 기준

기존 작업 파일이 없다면 아래 두 문서만 생성하고, 있으면 이어서 갱신한다.
- Docs/Plans/ROGUELIKE_ARCHITECTURE_PLAN.md
- Docs/Reports/ROGUELIKE_ARCHITECTURE_REPORT.md

PLAN에는 RA-A~D의 대상·의존성·필수 수용 조건·검증·담당·진행·예산을,
REPORT에는 실제 실행 증거·미검증·Finding·남은 작업을 기록한다.
변경 코드의 1:1 CodeMap 및 직접 영향 색인은 동기화하되,
새 설계서·회의록·역할별 보고서·완료 문서 재검토 묶음을 양산하지 않는다.

본 Goal은 RA-A~D를 실행 전에 고정한 독립 작업 단위로 승인한다.
이번 작업의 검토 예산은 단위별 최초 검토 1묶음(네 단위 합계 최대 4묶음),
최초 검토 이후 수정·재검증은 단위별 최대 2묶음(네 단위 합계 최대 8묶음)이다.
최초 검토와 수정·재검증의 집계는 구분한다. 이는 AGENTS의 기본 Task 단위를
이번 작업에 한해 사전에 명시한 사용자 승인이다.
이 숫자는 소진할 할당량이 아니라 상한이다. 통과하면 남은 횟수를 쓰지 않고 종료한다.
파일·하위 작업·세션을 사후 분할해 예산을 추가하지 않는다.
같은 원인의 미해결 Finding과 횟수는 단계나 세션이 바뀌어도 원래 소속 단위에 승계한다.
D 종료 후 최종 통합 검증은 별도 검토 예산을 만들지 않는다. 발견된 회귀는
원인 단위의 남은 예산에서 처리하고, 같은 수정 묶음을 둘 이상의 단위에 중복 집계하지 않는다.
후속 발견을 이유로 통과했던 전체 설계를 다시 검토하지 않는다.

구현 중 정상적인 TDD Red/Green과 증분 빌드를 별도의 설계 검토 회의로 세지 않는다.
최초 검토에서 확인된 결함의 수정은 누적 예산으로 관리한다.
원인과 조치 없이 동일 실패 도구/테스트를 계속 반복하지 않는다.

보조 에이전트는 실제 사용 가능하고 효과가 있을 때만 사용한다.
이번 Goal에서 동시 최대 3명(메인 포함), 누적 보조 위임 최대 4건, 재귀 위임 금지.
공통 계약·상태·설정·자산·PLAN/REPORT 통합 담당을 정하고 같은 파일에 동시에 쓰지 않는다.
Unity 실행은 메인 1명만 담당한다. 도구가 없으면 단일 실행으로 진행하고 위임을 흉내 내지 않는다.

범위 안의 되돌릴 수 있는 기술 선택·시험 수치는 근거를 PLAN에 기록하고 진행한다.
게임 핵심 규칙 변경, 데이터 손실, 추가 설치/비용/권한이 필요한 경우만 해당 부분을 차단한다.
선행 검증이 통과한 단계는 종료하고 다음 단계로 이동한다.
일반 개선 아이디어는 FOLLOW_UP으로 남기고 필수 작업을 늘리지 않는다.

수정 한도 소진 시 완료로 포장하지 말고 BLOCKED로 남긴다.
실제 테스트 실패는 FAIL로 기록한다. 권한·필수 계약·예산 문제로 진행할 수 없으면 BLOCKED,
필수 실행 검증을 기다리면 WAIT_VALIDATION, 아직 실행하지 않은 개별 시험은 NOT_RUN이다.
NOT_RUN이 있는 전체 범위를 무조건 COMPLETE로 요약하지 말고 로컬 구현과 플랫폼 검증을 나눠 보고한다.
실행/컨텍스트 한계로 중단되면 현재 diff·완료 항목·미완료·다음 검증·누적 횟수를 기록한다.
자동 재개나 백그라운드 작업을 약속하지 않는다.
