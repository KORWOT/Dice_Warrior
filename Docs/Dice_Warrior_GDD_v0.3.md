## 확정 게임 루프

Android 세로 화면, 모험가 1명, 적 1명. 로비 준비 → 이동 D6 → 착지 사건 → 한 바퀴 보상 → 다음 지역 → 지역 3 보상 → 최종 보스 → 결과 정산 → 영구 성장.
전투는 검·지팡이·불·방패 기호 주사위 1개로 시작한다. 지역 1·2 완주 보상으로 2·3개가 된다.
6면 기호 주사위의 분포를 고르고 교체하며 장비 3칸(무기·방어구·장신구)을 준비한다.
카드 소유·학습·와일드 카드·6D6 족보·운명력·재굴림·분기 지도·전투 스킬 선택은 제거한다.

## 전투 계약

전체 눈의 순서 무관 멀티셋과 정확히 일치하는 조합 기술 **한 개**를 발동한다.
부분 조합을 찾지 않는다. 불일치하면 주사위 순서대로 모든 기본기를 실행하며 같은 눈도 각각 한 번이다.
기본기와 조합기는 같은 피해/보호막 계산을 쓴다. 장비는 기술 태그에 맞는 보너스만 준다.
수호는 보호막 기술의 효율이며 상시 피해 감소가 아니다.

- D1: 적 사망 이후 계획된 기본기는 `enemy-defeated`로 생략 기록. 계획·적용·생략을 구분한다. 죽은 적은 반격하지 않는다.
- D2: 적 보호막은 플레이어 기술 묶음 전체에서 차감하고 남은 양은 묶음 끝에 만료한다.
- 살아 있는 적은 예고된 공격/강공격/방어 중 하나를 한 번 실행한다. 플레이어 보호막은 반격/턴 종료 뒤 만료한다.
- 면 결과·기술 ID·효과·적 의도·턴 전후 HP/보호막을 저장한다. UI 재표시·재개는 확정 로그만 읽는다.

## 캠페인 계약

지역당 12칸: 시작 0, 사건 1..11. 이동 D6 1개, 착지 타일만 처리한다.
`위치 + 눈 >= 12`이면 위치 0의 완주 보상 대기로 전환하며 초과 이동을 버린다. 일반 타일 사건은 없다.
지역 보드는 시드와 지역 번호에서 파생한 별도 RNG로 한 번 생성하고 저장한다. 전투 RNG와 독립적이다.
각 보드에 전투·이벤트·보물·상점·휴식이 모두 존재한다.
완주 보상은 `runId:region:lap` ID로 한 번 확정한다. 지역 3의 보상도 보스 **진입 전** 받는다.

## 성장·선택·시험값

다음 수치는 밸런스 확정이 아닌 MVP 시험값이며 설정 SO에서 새 런에 반영한다.

| 항목 | 첫 시험 |
|---|---|
| 시작 능력 | HP 60, 위력 5, 수호 4 |
| 기본기 | 검: 피해 위력+2, 지팡이: 위력+1, 불: 위력+3, 방패: 보호막 수호+3 |
| 2눈 조합 | 검+지팡이 검기, 지팡이+불 화염탄, 검+방패 수호 베기 |
| 3눈 조합 | 검+지팡이+불 화염 검기, 검+방패+방패 성채 베기 |
| 일반 전투 | 지역별 적 HP·공격 증가, 승리 XP 5/골드 12 |
| 레벨 | 필요 XP=현재 레벨×8, 상승 시 최대 HP+6/현재 HP+6/위력+1/수호+1 |
| 완주 | 골드 15, XP 5, HP 12 회복; 지역1·2 주사위 추가, 지역3 장비 선택 |
| 영구 정산 | P2 새 제출은 명령 재현 성공 시 완료 지역×10 + 최종 승리 20 지급. 이전 P1 대기 기록은 지급 0 보존 |
| 영구 성장 | 다음 단계 비용 20×(단계+1), 다음 새 런 최대 HP+5 |

로비에서 시작 주사위 종류와 무기를 선택한다. MVP 준비물은 공통 해금된 세트이며 영구 보유품 수집은 보류한다.
이벤트는 HP 대가와 골드/XP 중 선택, 휴식은 회복/훈련 선택, 보물은 장비/주사위 교체 선택, 상점은 골드를 쓰는 회복/장비/주사위 교체를 제공한다.
교체는 장비 슬롯 또는 주사위 슬롯을 명시하고 거절/뒤로 가기를 제공한다.
선택 후보를 저장하며 화면 재진입에 재추첨하지 않는다. 전투 중 교체는 불가하다.
런 XP·장비·골드는 런 내부 값이다. 영구 재화와 성장 단계만 다음 런으로 이어진다.

## 실행·저장·화면

`SymbolLoop`가 유일한 게임 기능이다. 순수 도메인 → 세션/저장 → 화면으로 의존한다.
새 런은 Mock 백엔드가 발급한 시드·규칙 버전·성장/출전 스냅샷으로 시작한다. 이동/전투 세션 명령은 후보 복제 → 토큰/규칙 검사 → 저장 성공 → 공개 순서다.
요청 ID/입력/revision/복구 세대로 중복·오래된 입력을 구분한다. 재시도는 같은 요청을 사용한다.
체크섬 파일과 마지막 정상 백업을 사용하고 손상 시 자동 초기화하지 않는다. 복구는 백업 확인 후 명시 입력으로 실행하고 세대를 올린다.
M0~M3 이후 체크포인트 경로는 `Application.persistentDataPath/symbol-loop-backend-v1/http-mock/<endpoint+계정 SHA256>/checkpoint.json`, 서버 권한 저장은 `Server/data/authority.db`다. 구형 `mock/checkpoint.json`·`authority.json`·`symbol-loop-v1/player.json`과 백업은 열거나 삭제/이관하지 않는다. 서버를 먼저 실행하는 방법은 [Server/README](../Server/README.md)를 따른다.
Title.unity 하나에서 로비/보드/전투/보상/결과를 전환한다. 고정 UI는 Editor에서 작성한 프리팹, 반복 타일·선택지는 작성된 슬롯을 바인딩한다.
공통 uGUI 기반과 폰트·외부 플러그인을 유지한다. 장치 실플레이·밸런스·최종 아트는 별도 확인 대상이다.

## 보드·주사위·스킬 표시 계약 (2026-10-21)

사각 둘레의 12칸에서 전사 말이 시계 방향으로 이동한다. 숫자 D6의 면이 회전·감속해 확정 눈을 보여준 뒤 말이 한 칸씩 튀며 이동한다. 출발점 통과 시 0번에 멈추고 초과 칸을 버린다. 사건 화면은 착지 후 열린다.

전투에서는 보유한 1~3개의 주사위가 실제 여섯 기호 면을 가진 입체 Canvas 메시로 회전한다. 정지 면은 저장된 결과다. 전체 조합 안내 후 조합 스킬 1개, 또는 기본기를 눈 순서대로 표시한다. 검격/마법/화염/방어는 각각 기호·색·이동/충격 효과를 가지며 스킬 이름, 피해/보호막, 체력 바를 함께 갱신한다. 처치 뒤 생략된 스킬과 없는 반격은 표시하지 않는다. 적용된 플레이어 기술 뒤 기록된 적 공격/방어를 표시한다.

연출은 저장 성공 후 전후 상태와 턴 로그를 소비한다. 게임 RNG나 피해 계산은 재실행하지 않는다. 재생 중 명령 입력을 잠그고, 앱 비활성/백그라운드/화면 닫기/다시 불러오기는 최종 확정 상태로 복귀한다. 연출 중 종료해도 이미 저장된 결과를 다시 지급하지 않는다.

코드로 그린 벡터 아트와 입체 투영 방식이며 Rigidbody 물리 주사위·최종 캐릭터 아트·음향은 이번 범위에 포함하지 않는다. 세로 720×1280 기준 레이아웃을 가용 safe area에 균일 축소/확대한다. 구현 및 실제 검증 상태는 [화면 PLAN](Plans/SYMBOL_LOOP_PRESENTATION_PLAN.md) / [화면 REPORT](Reports/SYMBOL_LOOP_PRESENTATION_REPORT.md)를 따른다.

온라인/결제/Firebase/PvP, 다중 적, 이동값 선택, 주사위 제작, 최대 4개 이상, 일반 트리거 엔진, v1 런 이어하기/변환은 구현하지 않는다.

## Mock 권한 분리 P1 기준과 보존 정책 (2026-10-21)

- `protocolVersion=1`, `rulesVersion=symbol-loop-mvp-1`. 현재 12칸·3지역·1~3눈 콘텐츠와 RNG를 동결한다. 조건부 3/4눈 상위 기술은 보류한다.
- 영구 재화·성장과 새 런 승인은 IGameBackend가 담당한다. Unity의 profile은 캐시/표시이며 제출된 최종 승리·HP·재화를 지급 근거로 받지 않는다.
- 개발 계정은 최초 생성 시 성장 확인용 20재화를 한 번 받는다. P1에서 이미 제출한 런 기록은 PendingVerification/지급 0을 유지한다. P2 이후 새 제출은 아래 재현 정산을 적용한다. 제출 이후 다음 런은 가능하다.
- 권한 성장 비용은 Mock에서 계산한다. Mock 프로필/재화는 운영 데이터로 승격하지 않는다. 프로세스 내부 Mock은 보안 서버가 아니다.
- 서버 요청 전 동일 ID/본문을 디스크에 보존한다. 응답 유실·타임아웃·승인 후 기기 저장 실패는 같은 요청을 조회/재전송한다. 미결 요청이 있으면 새 ID 발급/임의 취소하지 않는다.
- 로컬 백업을 복원해도 권한 프로필은 서버에서 다시 조회한다. 백업에 없는 활성 승인 런은 시작 티켓으로 복구하고, 같은 런의 남아 있는 진행/명령 로그는 유지한다. 손상된 Mock 권한 파일은 자동 초기화/과거 재화로 복원하지 않는다.
- Firebase 선택은 현재 명시적 미지원이다. 정산 복구/동시성은 아래 P3 계약을 적용한다. Firebase/Emulator(P4), Android 출시 검증(P5)은 [로드맵](Dice_Warrior_Next_Work_MockBackend_Firebase_Roadmap_v0.1.md)의 후속 범위다.

## P2 명령 재현과 보상 정산 (2026-10-21)

Mock 권한 저장소의 시작 티켓(시드·규칙·출전·성장)으로 새 Run을 구성하고 `travel/combat/choose/lap/abandon` 로그를 순서대로 실행한다. 클라이언트의 최종 상태·승리·주사위 눈·지급액은 입력으로 받지 않는다. 명령별 순번, 고유 ID, `지역:위치:단계:턴` 대상, 비용·선택·장비 슬롯·종료 여부를 확인한다. Session과 검증기는 순수 명령 규칙을 공유하되 서로 다른 상태를 사용한다.

결과 단계까지 합법적으로 재현되면 완료 지역/승리에서 지급액을 계산한다. 프로필, 영수증, 런 종료와 요청 결과는 기존 Mock 원자 저장으로 함께 확정한다. 동일 요청이나 같은 런 재제출은 추가 지급 없이 기존 영수증을 돌려준다. 승인 영수증에는 검증 버전 `symbol-loop-replay-1`과 재현된 결과를 보관한다. 규칙 버전 `symbol-loop-mvp-1`과 기존 경제/전투 계산은 그대로다.

검증 거절은 활성 런과 재화를 보존하고 실패 코드·명령 순번을 표시한다. 같은 요청 ID의 내용은 바꿀 수 없으며 정정 로그 제출은 새 요청 ID를 사용한다. 요청 상한은 2048명령/512KiB, 권한 측 60초 창의 시작 10회·새 제출 20회·포기 10회다. 같은 ID 재시도와 기존 영수증 조회는 빈도를 추가 소모하지 않는다.

고정 시드 33/51/19/1의 승리·패배·포기·상점/교체 기록과 각 명령 이후 주요 상태/RNG를 JSON으로 동결한다. 2·3기호 조합과 직렬화 재개도 비교한다. 구현·증거는 [P2 PLAN](Plans/SERVER_RUN_REPLAY_VALIDATION_PLAN.md) / [P2 REPORT](Reports/SERVER_RUN_REPLAY_VALIDATION_REPORT.md)를 따른다.

이 검증은 불법 상태 전이와 결과값 위조를 거절한다. 합법적인 다른 행동 로그를 구성하거나 미래를 예측하는 자동 플레이까지 판별하지는 못한다. 프로세스 내부 Mock 파일/코드 변조 방어와 운영 서버 보안은 Firebase 이전 및 별도 검증 범위다.

## P3 정산·비동기 복구·동시 실행 (2026-10-21)

정산 전 요청 ID와 본문을 디스크에 저장한다. 응답 유실·단절·취소 시 지급 결과를 미확정으로 표시하고 같은 요청을 조회/재전송한다. 요청 본문이 바뀌면 거절한다. 서버에서 지급했어도 로컬 저장이 끝나지 않았다면 같은 영수증을 복구하며 추가 지급하지 않는다. 이미 로컬 확정까지 끝난 뒤 최신 프로필 조회만 실패한 경우에는 승인 결과를 유지하고 재조회를 안내한다.

읽기 전용 런 조회는 시작 티켓·원 제출 영수증·저장된 명령과 최신 프로필을 반환한다. 과거 백업이 정산 전 상태라면 승인 명령을 재현해 결과를 복구한다. 기존 P1 대기 영수증은 새 검증/지급 없이 그대로 보존한다. 서버가 다음 런을 시작한 경우 이전 런 정산을 먼저 합치고 새 활성 런의 시작 티켓을 복원한다. 교체되는 로컬 원문은 `.reconciled-<id>.json`에 보존한다. 같은 활성 런의 남아 있는 로컬 진행은 유지한다.

같은 런의 동시 제출은 영수증 한 개와 지급 한 번으로 끝난다. 서로 다른 세션의 같은 revision 구매 또는 구매/정산 경합은 한 변경만 승인하고 패자는 최신 상태를 다시 읽는다. 로컬 저장은 같은 경로의 잠금과 revision/generation 비교를 사용한다. 자동 pending 정리는 관찰한 ID만 대상으로 하므로 새 입력을 지우지 않는다. 오래된 권한 응답은 최신 프로필과 완료 런을 덮을 수 없다.

화면은 정산 중/결과 불명에 `보상 검증 대기`를 표시하며 확정 전 지급 성공으로 표시하지 않는다. pause/disable 뒤 재개와 화면 재생성에서도 미결 요청은 남고, 같은 요청 확인 후 승인 결과 화면으로 돌아간다. 오류 진단에는 원 요청·응답·실제 예외를 보존한다.

P3 당시 검증 범위는 같은 프로세스의 독립 로컬 체크포인트 두 개와 공유 Mock 권한 저장소였다. 실제 네트워크 대신 전송 전/지급 후 단절·취소를 주입했다. 별도 프로세스가 동일 Mock JSON 파일을 직접 공유하는 구성은 지원하지 않는다. 당시 승인은 P3까지였으며 증거는 [P3 PLAN](Plans/SERVER_SETTLEMENT_SAFETY_PLAN.md) / [P3 REPORT](Reports/SERVER_SETTLEMENT_SAFETY_REPORT.md)에 보존한다. 이후 승인된 HTTP/SQLite 작업은 아래 M0~M3 계약으로 구분한다.

## 독립 Mock 서버 M0~M3 (2026-10-22)

사용자 승인 범위는 별도 서버·SQLite·Unity HTTP 연결까지다. 같은 저장소의 `Server/`에 ASP.NET Core 호스트, 권한 서비스/검증기, SQLite 저장소를 둔다. 서버는 Unity 설치 없이 별도 프로세스로 실행한다. Domain 소스와 LoopJson을 링크 컴파일하며 게임 규칙·프로토콜·골든 벡터는 유지한다. 버전별 서버 콘텐츠 JSON과 Unity Config의 동치를 검사한다.

Unity의 기본 백엔드는 HttpMock이다. 프로필·런 시작·제출·성장·작업 조회·런 조회의 6개 HTTP 경로를 사용하며, 즉시 이동/전투는 로컬에서 처리한다. 개발 계정은 루프백 헤더로 선택한다. Editor/개발 빌드와 서버 Development 환경에서만 허용한다. 응답 유실·취소·서버 재시작 후에도 기존 요청 ID/본문을 보존하고 영수증을 다시 확인한다. 자동 인프로세스 전환은 없다.

SQLite는 WAL과 사용자별 저장 버전 비교를 사용한다. 런 재현은 쓰기 트랜잭션 밖에서 수행하고, 짧은 트랜잭션 안에서 최신 버전과 유니크 키를 확인하여 프로필·런·영수증·작업을 함께 확정한다. 같은 DB의 복수 서버 프로세스를 검사한다. 구형 파일 권한 저장소는 Editor 회귀 검사 전용 DLL로만 남기고 플레이어에는 포함하지 않는다.

기존 P1 대기0/개발 계정 최초20 정책과 P2/P3 정산·복구 의미를 유지한다. 기존 실제 저장을 새 서버 DB로 자동 이관하지 않는다. M0~M3 당시 후속이던 계측·비용은 아래 M4로 추가 승인됐다. [M0~M3 PLAN](Plans/STANDALONE_MOCK_SERVER_01_PLAN.md) / [REPORT](Reports/STANDALONE_MOCK_SERVER_01_REPORT.md)의 완료 증거는 보존한다.

## M4 사용량·비용 확인 (2026-10-22)

별도 서버의 /dev/dashboard에 로컬 HTTP·SQLite·재현 벽시계·프로세스/파일 실측, Firestore 문서 접근 가정, 운영 실측 없음의 세 범주를 구분한다. 계측 실패가 지급 결과를 바꾸지 않고, 응답 유실과 권한 승인도 각각 보존한다. 원본 신원·요청/런 ID·명령 내용 없이 가명 메타데이터만 유한 보관한다.

서울 Firestore Standard/USD·무료 할당량 미차감을 기본으로 최소/기준/최악 비용 시나리오를 계산한다. 실제 Firebase 연결이나 운영 과금/성능 측정이 아니며 게임 경제·보상·규칙·프로토콜을 변경하지 않는다. 가격/무료 구간·전송·저장·Cloud Run 가정과 제외 비용을 명시하고 미지원/결과 불명은 미산정으로 둔다. [M4 PLAN](Plans/STANDALONE_MOCK_METRICS_04_PLAN.md) / [REPORT](Reports/STANDALONE_MOCK_METRICS_04_REPORT.md)와 [서버 안내](../Server/README.md)를 따른다. M5 규모별 부하 시험·실제 Firebase·Android는 후속 범위다.
